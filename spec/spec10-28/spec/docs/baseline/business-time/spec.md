# 系统日本业务日期与事件时间规格

2026-10-04最新裁决：整个系统部署和使用于日本时按日本业务时间正确运行，适用于若依系统能力、C01～C03及后续业务。**取代此前强制UTC存储/UTC Z响应、公共时区不得调整及PROP独立时间口径的要求。** 技术方案优先现有框架/依赖配置，仅对配置无法解决的具体问题补代码，不新增时区框架。

本规格是目标行为，不表示现有实现或历史已符合。验证见[validation.md](validation.md)；具体业务日期、更正、编号来源仍按各功能正文。

## 1. 时间分类及接口契约

| 类别 | 存储及接口约定 | 最终消费 |
|---|---|---|
| 事件时刻：创建/修改/确认/关系/解除/审计 | 现有DATETIME以东京当地年月日时分秒为约定，不自带时区；事件接口响应采用ISO8601带数字偏移，日本输出例如`2026-10-04T11:47:46+09:00`。其他存储类型按真实语义核对，不机械改列类型 | 整个系统按Asia/Tokyo展示，排序按实际时刻，不能因浏览器所在地改变 |
| 业务日期：受注/寄送/首次出货 | `YYYY-MM-DD`；不附时刻/偏移再换算 | 保持员工采用的日历日期，默认今天取日本业务日 |
| 业务月份：生命周期基准月 | `YYYY-MM`；由功能规定业务日期取年月 | 不由操作时刻替代，不按小时平移 |

字段必须登记类别、来源、实际精度、格式及空值含义。允许员工输入事件时刻的接口要求Z或明确数字偏移，按同一时刻归一到日本口径；无时区事件输入拒绝，不猜浏览器/宿主区。服务器操作时间由服务器生成，审计字段不得成为客户端伪造事件的入口。纯日期/月拒绝非法格式和日历值，不静默截断；可空为null，不用空字符串/零日期/当前时刻补造。

页面、导出、日志及新文件的时间口径应可识别为日本时间；可简化显示，但不能混淆事件与纯日期。接口含偏移不表示数据库列包含偏移；读取DATETIME时必须采用既定日本解释。既有冻结内容按§5处理。

## 2. 同一业务事件的关联记录

同一次事件的关联记录共用一个事件时刻。例如确认寄出、由其建立的订单关系与相关确认事实时间一致；解除是之后的独立事件。不同动作/逐台独立事务不强行一个时间。

重复请求/重放不刷新原时刻；寄送业务日期更正不重新确认，不混改操作时刻。实际列精度与响应一致，不补造未存毫秒。

## 3. 排序、显示及共享能力

历史按实际事件时刻及功能方向排序，同时间稳定次序，空时间不补当前时间。禁止固定小时补偿或只修比较器掩盖混合来源。

日本、中国、UTC及其他浏览器下均按Asia/Tokyo显示；纯日期/月不偏移。若依日志、用户/角色等审计、任务日志、导出及PROP采用相同口径，不维护两套规则；现有类型、注解、Map和工具按真实消费核对，避免重复转换。

## 4. 日本日历、筛选与调度

今天、默认日期及以当前年度为依据的编号采用日本日历。编号以当前时刻还是指定日期为依据仍按功能规定；不重置历史号/序列/重放身份。

日本日期筛选事件采用该日到次日左闭右开区间。东京DATETIME可用当地边界；时间点类型输入/存储按实际类型转换等价边界，不能机械套用DATETIME规则。选定末日包含整日，不用23:59:59遗漏小数精度。纯DATE直接按日历值比较。

生命周期月份源自指定业务日期。适用日本日历任务按Asia/Tokyo执行；默认时区调整影响Quartz/日志/导出等须核对。原任务语义不明先列缺口，不静默改变外部约定任务再称通过。

## 5. 历史及冻结内容

可靠区分原UTC、中国、日本及未知来源。仅来源/转换规则可确认且对象范围获批才修正；不以固定差值、当前配置或记录顺序猜全表。保留原值、依据、范围、结果及防重复执行证据。

未知保持待核实，不伪装为日本时间、不补当前时刻、不宣称历史正确。业务日期/月不按小时平移；旧默认日错误另批。既有冻结邮件/文件/快照不静默重写；新版本与旧内容分别验证。

## 6. 切换与验收

优先配置JVM/JSON/驱动连接及SQL会话，补充配置不能解决的代码。存储、映射、接口、显示、筛选、调度及多表时间形成完整链路；不能用配置存在/离线测试代替实际运行。

部署必须有一致的代码、配置、数据解释边界和停止写入窗口；不得混用旧代码/新配置/未处理混合历史。新写入与历史处置分别授权验收，未验证保持待办。
