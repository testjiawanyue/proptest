# FEAT-20 历史客户与订单补录

状态：2026-10-22按用户已确认交互整理的正式需求；未实现、未授权编码、迁移或导入。本功能为独立补录闭环，不改变正常新客户、生产、订单及寄送的入口。下列规则来自本次用户裁定；技术落点见对应OpenSpec Change。

## 1. 用户、目的与范围

PROP员工补录已确认的老客户，以及历史商品/租赁/代替品订单（首次交付、回收后的再次出租，以及已实际结束的历史出租）、产品和当前部件关系，使后续正常业务可识别这些产品。新客户继续正常创建。历史补录不要求客户准备上传文件，不提供文件导入、草稿、审批或连续录入。

客户补录复用现有「顧客管理」列表及公司/支店编辑弹窗，只新增「過去の注文を登録」独立页面。现有客户页增加历史公司/支店创建入口：正常新增自动配号，历史新增填写原号。先保存公司，再在已有公司下逐个保存支店；每次保存一个主体及其地址、联系人，不提供多主体客户图。

先在客户管理独立保存所需资料，再填写历史订单；离开页面不保留输入，提示丢失风险，不建设跨页恢复。订单仅引用已保存客户。

不纳入：配件、库存批次、正在进行的点检维修/返送业务、销售/代替品的后续再次交付、历史全量作业过程（已结束租赁订单可逐单补录，但不补造整套旧作业链）。补录保存的是目前经人工确认可用于后续业务的信息，不承诺还原资料未记录的过去情况。

### 1.1 操作入口与完整交互流程

客户与订单是两个独立保存的业务对象，不新增“客户/订单”双页签工作台。历史客户可单独补录，不必先开订单。

| 步骤 | 操作人员操作 | 系统反馈与保存边界 |
|---|---|---|
| 1. 打开历史订单补录 | 在订单管理进入「過去の注文を登録」 | 展示订单信息、三个客户角色、产品明细及提交操作；初始销售，不默认历史日期 |
| 2. 填订单并选客户 | 填完整原订单号、受注日、产品需求，分别选下单方、納品先、付款方 | 展示三方实际选择；配送地址及联系人随納品先逐级选择 |
| 客户准备 | 录订单前先在客户管理补齐资料 | 离开订单页提示输入将丢失，返回不恢复、不自动采用 |
| 5. 添加产品 | 逐台添加或粘贴多行制造编号，明确采用已有产品或建立新产品 | 添加仅生成输入行；制造编号与衣体编号共用一个输入；已有产品显示已有配置，不覆盖 |
| 6. 补齐产品信息 | 新产品填写衣体规格与版本、已知部件；填写每台真实本单出货日 | 部件默认展开；未知部件/固件明确留空；统一填写工具只补符合条件的空白项 |
| 7. 提交与修改 | 点击提交，按提示人工修改后再次提交 | 必填、客户归属、产品及部件占用、日期和关系统一校验；明确失败不留下本次订单的部分数据 |
| 8. 完成 | 查看成功结果及详情入口 | 保存整张订单及其本次新建产品、绑定和历史依据；不自动清空并开始下一单 |

首次交付与再次出租由操作人员结合真实业务明确选择，不由“查不到产品”自动推断。首次交付只填一次真实出货日，系统据此建立首次日期和基准月；再次出租填写本次日期，显示并保留原首次日期和基准月。具体准入条件见§3.3。

### 1.2 页面字段概览

下表用于业务阅读，完整条件和修改限制以§2～§4为准。

| 位置 | 必填内容 | 可选内容或条件 |
|---|---|---|
| 历史公司创建 | 原客户编号、公司名称、客户区分（默认直販，可选择） | 地址和联系人可不录；添加地址/联系人时须满足各自必填规则 |
| 历史支店创建 | 已保存的所属公司、原客户编号、支店名称 | 客户区分继承公司；地址/联系人同上 |
| 每个地址 | 邮编、地址1 | 地址2单列可空；所属公司/支店明确显示 |
| 每个联系人 | 所属地址、姓名 | 职称、电话、传真、邮箱、备注可空 |
| 历史订单 | 完整原订单号、受注日、类型、三个客户角色、納品先地址、对外产品名称、按不重复产品明细自动计算的数量 | 联系人、客户订单号、预计发货日、备注可空；颜色要求可空 |
| 每台产品 | 制造编号、采用方式、真实本单出货具体日 | 新建产品须衣体规格及版本；已有产品引用并校验；首次/再次出租按§3.3 |
| 其他部件 | 已填写部件号时，须明确类型及规格版本 | 未知编号可空；传感器固件未知可空，不生成假值 |

### 1.3 用户可见的关键提示

- 离开订单去客户管理时提示：离开后将丢失未提交输入；建议先补齐客户，再填写订单。返回不恢复。
- 客户保存成功提示客户已保存；返回订单后仍需选择该客户并提交订单。订单失败不撤销已经保存的客户。
- 产品或部件冲突须指出具体产品行、编号及冲突原因，不提供强制覆盖按钮。
- 再次出租突出显示“原首次出货日/基准月保持不变”；缺失原基准或回收依据时提示核对，不代造记录。
- 提交结果未知须明确显示“尚未确认保存结果”，提供查询/原样重试，不能提示用户重新创建一笔。

## 2. 复用现有客户管理

### 2.1 公司、支店与编号

- 一个公司可以有多个直属地址、多个支店；支店可以有多个地址；每个地址可以有多个联系人。只有公司/支店两层，不新增现场第三层实体。
- 新补录公司/支店必须有原客户编号和名称。支店必须引用有效一级公司，不能用支店作为上级，也不能以支店编号代填无编号的公司。无地址、无联系人可独立保存客户。
- 历史编号首次补录可填写，保存后不可修改；全局唯一口径沿现有数据库。禁止自动去前导零、改变大小写、移除符号或把多个旧编号合为一个。
- 历史创建不接收已有主体修改命令；同号时提示打开现有客户。保存后的资料统一走现有完整编辑：编号、类型及上级不可修改，其他资料按正常维护规则处理。地址/联系人必须先读取完整集合再编辑，不能把局部追加载荷传给全量更新；正常明确删除的行为保留。
- 同一实体不得重复创建不同编号。系统能保证既有实体编号不可变、同号不重复，不能仅凭同名自动认定同一公司；同名只提供重复候选提示，不作名称唯一约束。
- 公司默认客户区分沿现有「直販/代理」规则；新补录默认直販，页面明确显示并允许选择。支店继承母公司区分，不保存独立区分。此默认是业务录入默认值，不声称从历史材料推断出直販事实。

### 2.2 地址与联系人

地址所属公司/支店由填写位置明确，直属公司地址显示「会社直属」。地址1、地址2分别填写。新增地址时邮编与地址1必填；邮编为7位半角数字，数据库保存7位数字、展示〒XXX-XXXX；地址2可空。联系人姓名必填，职称、电话、传真、邮箱、备注可空，沿现有文本保存规则，不新增强制国际电话/邮箱格式校验。

订单中的已有地址/联系人只读引用；客户管理继续完整编辑，新增联系人必须挂在明确地址下，不允许跨主体转移。不自动把母公司地址借给支店，也不把同一地址文本去重为跨主体共享地址。

## 3. 独立历史订单页面

Q1～Q3已由用户确认，最新裁决见§7；历史资料不足时不得用默认值冒充事实。

### 3.1 订单及三个客户角色

- 原完整注文管理番号必填，保留子订单后缀；不消费当前年度编号序列。历史订单号允许重复，以内部订单ID区分；不提供同号或相似旧单候选，不自动归并主子订单。
- 受注日必填，不默认今天；客户订单号、预计发货日、备注可空。订单类型允许销售sale/租赁rental/代替品replacement，不提供配件；初始销售。订单客户区分为direct/agency，默认可采用下单公司区分，操作人可以修改。
- 下单方、納品先、請求書付款方分别采用公司/支店，不要求同一母公司。付款方可以明确采用“同下单方”；最终保存必须解析到有效对象，不接受任意自由快照。沿正常订单的三方默认行为，但三方结果始终展示可见。
- 配送地址必须直接属于本单納品先；联系人可空，填写时必须属于该配送地址。变更納品先清空原地址和联系人，变更地址清空原联系人。
先在客户管理独立保存所需资料，再填写历史订单；离开页面不保留输入，提示丢失风险，不建设跨页恢复。订单仅引用已保存客户。

### 3.2 需求与产品

- 对外产品名称选择已有名称；一个订单一种名称，数量由服务端按不重复的产品明细计算，前端只读展示；不填写原需求数量或设计资料未补齐余额。颜色可空，不校验实物颜色，不把产品分配给颜色行。
- 至少一台不重复产品，订单数量由服务端按明细计算，不保留原需求量或补齐余额。
- 本入口产品清单表示操作人确认已真实交付的产品；租赁逐台区分仍在出租与已回收结束，后者不建立当前占用。仅在旧台账出现过编号不等于已确认交付。当前关联准入与已结束历史记录分别按§8校验。当前另有订单、寄送准备、已删除/报废或尚未结束的在途作业冲突时不得强制覆盖；有正在进行维修/返送的产品不通过本入口改状态和关系。
- 制造编号就是衣体编号，仅输入一次；系统保存产品身份、衣体身份及body绑定。新产品必须选明确的衣体资料及其规格版本；不能仅凭编号推规格。
- 其他槽位为气囊、传感器、发生器1、发生器2；每台默认全部展开，新增可填写、已有只读，不要求点击展开。用户已确认：未知部件编号或固件允许留空并明确显示；不生成假部件或默认最新版固件。填写了部件号就必须明确类型、资料版本，已有个体只读引用；固件只适用于传感器。
- 当前绑定表达“本次确认的当前配置”，不声称是原始出货配置。不自动建立每年的更换历史，也不将补录时刻当作原安装时刻。
- 同一产品槽位不能重复，同一部件不能占用两个槽位或两个产品。已绑定本产品且一致的对象直接引用；已有产品/部件/绑定不一致时提示冲突，不自动换件、改规格、升级固件或清空未知项。

### 3.2.1 逐条录入与批量粘贴制造编号

产品区域同时保留「逐条添加」和「批量填写制造编号」。批量方式只读取人员主动粘贴的纯文本：从Excel复制单列编号，在小弹窗内一行一个编号，点击「添加到明细」生成本单产品行；不上传文件、不自动读取剪贴板、不另设产品页签。

- 接受LF、CRLF、CR换行；逐行去掉首尾空白，忽略空行，按原顺序追加。保留前导零、大小写、全半角及内部符号，不推断连续范围、不自动去表头或转换编号。含Tab的多列输入拒绝；逗号/分号不作为分隔符。
- 每个编号仍按制造编号规则校验非空及最多64个Unicode码点，不新增年份/型号前缀规则。单次最多200个非空编号、原文本最多20,000码点，超限提示分次加入，不截断；200是本地单次操作保护，不是订单产品总数上限。
- 本批相同编号、与现有明细相同编号均指出原始粘贴行号及冲突行，不静默去重。有任一格式、重复或数量上限问题，本批一行也不追加，保留弹窗文本和已有明细，修改后再添加。前端相等比较不能替代数据库排序规则；服务端最终按现有唯一性及占用约束校验，不自动归并大小写/字形相似的编号。
- 每台作为独立明细，追加后与逐条输入使用同一产品字段、查号/采用和校验规则，错误始终定位到对应产品。加入明细只代表编号已填，不表示产品已建档或关系已确认；规格、出货日等必填仍须完成，已知部件须校验，未知部件/固件仍允许空。可见的统一本单出货日已填写时带入新行并可逐台调整，未填则留空，不默认今天；不覆盖已有明细。
- 取消/关闭弹窗只丢弃本次粘贴文本，不改已有明细；成功添加后清空并关闭，重开为空。逐条与批量可以交替使用；改变编号后清除该行旧查号结果及采用身份，重新按原流程采用。
- 添加只填写当前表单，不保存、不占号、不批量自动查号。最终仍通过同一个订单提交一次原子保存。订单提交中、结果未知、身份冲突或已成功时禁止编辑和打开/确认粘贴；结果查询、原样重试及安全退出按原规则保留。

### 3.3 本单出货日、首次出货基准与租赁再次出租

每台必填一个本单真实出货具体日（YYYY-MM-DD），不默认今天。同单可统一填空白日期后逐台调整；统一动作不覆盖已填日期，不编辑首次日或基准月。未知具体日不能提交，不能用受注日、月份、月初日或登记日代替。

交付顺序与当前关系分开判断，不能用已有基准或当前占用推断历史交付是否允许补录。

| 交付顺序 | 采用条件 | 日期与基准处理 |
|---|---|---|
| 真实首次交付 first（销售/租赁/代替品） | 确认本单为真正首次；可新建或引用已有产品，不因已有较晚基准或有效交付拒绝 | 本单出货日是首次候选；无基准则建立，更早经统一确认前移，同日不换源；已有更早依据与“本单真正首次”矛盾时提示纠正采用方式，不覆盖更早事实 |
| 再次出租 rental_repeat（仅租赁） | 确认本单不是首次；已有产品或依据旧资料新建均可；不选最近回收记录、不检查跨订单出租顺序 | 完整首次来源只读保留；没有首次记录须填写真实外部首次日且不晚于本单日，不用本单日冒充；本单早于当前基准时必须另填经核对的真实首次日期，不晚于本单日；仍为再次出租，统一确认后以外部首次依据前移基准，不能把本单冒充first；日期不确定则暂缓 |
| 来源异常或真实首次日期未知 | 基准半缺、来源归属/日期不一致，或无法确认真实首次具体日 | 暂缓，不猜日期或自动修复 |

| 本次关系状态 | 当前占用/作业检查 | 保存结果 |
|---|---|---|
| 租赁仍在出租 ongoing；销售/代替品建立当前关系 | 必须无其他当前有效关系及阻断性在途作业/准备占用 | 建立本单当前关系，不填回收日 |
| 租赁已结束 ended（可搭配first或rental_repeat） | 不因目前在修、返送、准备占用或另有当前订单拒绝；删除/报废仍拒绝 | 实际回收日必填；只写本单已结束有效交付，不改变当前业务 |

**回收操作引导：**仅当本次要建立当前关系且系统现存占用冲突时，引导到受付工作台确认产品回收、再到作业管理执行正常回收；错误关联沿订单解绑处理。离开提示丢失输入，处理后重新填写，不自动结束旧关系。已结束历史不要求先结束当前另一订单，也不补造旧受付/回收作业。无权限时提示联系有权限人员。

不检查跨订单历史顺序或期间重叠；更早有效交付按§8调整首次基准。登记时刻不是历史回收日期。

普通首次分支仍防止重复首次；后补更早真实交付按§8的明确确认和来源修正规则处理，不因已有基准一律拒绝；再次出租分支不能把“已有首次日”当冲突。已有主档、当前部件、真实质检及已有业务快照均不覆盖；首次记录全无且依据真实历史日期补建的情况按上表处理。原基准存在但来源异常时仍需核对，不自动更换来源或修复日期。

受注日晚于本单出货日时，日期区仅提示“出货日早于受注日，请核对”；由唯一提交前确认弹窗统一确认原资料如此后保存，不自动修改日期、不新增审批。历史受注日、本单实际出货日、首次出货日不得晚于日本业务当天；预计发货日可在未来。不检查跨订单出租顺序；更早交付按§8.2确认并前移首次依据。

### 3.4 质检与下游

- 历史订单统一视为当时已合格交付，不设置合格确认勾选或人工确认字段；销售、首次租赁及代替品，无已有质检时按历史质检通过认定，业务日期采用真实首次出货日；标明历史补录认定，不伪造原质检人员或时分秒。
- 建立历史质检通过认定时，同时把对应产品主档的“首次生产质检已通过”标记置为通过；历史质检记录、产品标记及本次登记历史必须在同一事务中共同成功或共同回滚。产品标记只表达首次生产质检资格，历史业务日期与本次登记审计仍按本节分离。
- 既有真实质检记录原样保留，并保证其产品标记为通过。既有产品再次出租但没有已登记质检记录时，不因再次出租自动建立记录或修改产品标记。历史交付合格不代表产品当前合格，不绕过正常维修、回收和再次出货校验；不建立特殊质检未知状态。
- 已有再次出租产品沿用已有质检，不因再次出租重建或改写。外部历史新建产品自动建立历史交付合格认定，日期采用真实首次出货日，不采用本次再次出租日。未知部件/固件仍可空，已有配置不变。
- 基准要求真实首次日期、匹配月份及可辨识的首次来源；来源可以是首次寄送或外部历史确认；不增加仅月例外、基准状态或规则引擎。再次出租不重置生命周期和通知计算；不自动生成/发送通知。正常keep保留、clear清空日期/月及首次来源、回收保留有效交付的规则不改。
- 系统记录本次登记操作人和时刻，区别于历史业务日期。旧受付、快照、文件不回写，履历标明历史补录及本次业务日期。

### 3.5 统一衣体规格与版本

页面工具一次明确选择衣体资料和版本，仅填充已经明确为新建、且两项都为空的产品。跳过已有产品、已填写或只填一项的行、尚未采用的编号行，显示填入和跳过数量，不自动采用新建模式、不覆盖已填值。动作只改页面内存，最终服务端仍逐台校验资料、版本及类型。

## 4. 保存、错误与后续操作

流程为“填写→提交→校验→问题定位→人工修改→再次提交”。页面普通必填使用现有表单校验；服务端最终校验所有对象和并发条件，可一次返回多条已识别问题，定位到公司/地址/联系人或第N台产品槽位，不承诺穷尽并发变化。

明确拒绝不留下本次部分数据，页面保留输入。成功显示订单/客户编号、产品数量及结果链接，不自动清空继续下一单。客户与订单的结果未知分别按下述规则处理；请求结束即结束加载提示，持续显示尚未确认的结果，不永久转圈。

### 4.1 客户保存结果未知：按原编号人工核对

客户历史创建保留原编号唯一校验和单主体整体保存，不承诺精确重放某次客户保存结果。网络超时或响应丢失后，显示原编号并提示到现有客户管理查询；可保留尚在页面内的输入供人工对照，不另设客户请求号查询页面。

查到同号时，人员核对公司/支店类型、上级、名称及地址联系人，明确选择使用已有客户或进入正常完整编辑；系统不能将“编号存在”自动视为本次保存成功，不能自动覆盖。暂时查不到也不证明未保存，应等待刷新或进一步人工核对；人工决定再次保存时仍使用原编号，不改号规避冲突。并发同号最多保存一份，重复拒绝后仍走人工核对。若记录曾被删除或无法判明来源，交人工处理，不自动恢复或重建。

已明确保存成功但列表刷新失败，只重试查询。客户成功不会使订单自动保存或自动采用该客户。

### 4.2 订单保存结果未知：确认原次结果

历史订单号允许重复，因此不能仅凭订单号判断本次是否保存成功。保留原次提交的结果确认及原内容重试能力；成功重试不产生第二份订单、产品或绑定，提交内容不一致时提示冲突，不自动重新创建。

查询原请求和原内容重试仅在当前页提供。离开、刷新或关闭前提示输入及结果确认上下文会丢失；返回为空表单，不提供URL查询号恢复、专用跨页查询入口或原载荷恢复。离开后结果仍不确定则在现有业务列表/详情人工核对，不凭订单号单独判成功，不自动另建请求。已保存结果详情读取失败，在当前页只重试读取。

历史交付依据是系统内部支撑，界面显示历史来源且只读；不产生普通寄送编号、承运商、运单、文件或邮件。正常解除、回收可沿原规则处理这些关系：错误解除否定有效交付，回收结束当前关系并保留有效交付。历史累计交付仍计入累计，运行期实际出货统计按真实业务日期及来源识别，不按补录时刻误计。

## 8. 倒序补录及已结束出租（2026-10-26已确认）

本节与[产品判断细则](product-judgment-rules.md)共同取代前文及旧原型中“仅当前关联、排除已结束出租、已有基准绝不调整、repeat不得早于任何已登记出租”的限制。首次/再次表示真实业务顺序，不表示录入顺序。以下已确认业务规则不等于技术实现就绪。

### 8.1 已结束出租与回收日期

每台租赁产品明确选择“仍在出租”或“已回收，出租结束”，可统一填写再逐台调整。同订单允许混合；销售/代替品不使用该选择。

已结束须人员确认确已实际回收，并必填实际回收日（YYYY-MM-DD）；日期或回收事实无法确定则暂不补录，不提供“日期不明”选项。实际回收日不得早于本单出货日，出货日和回收日均不得晚于日本业务当天；同日允许，不采集时分秒。不检查跨订单历史日期重叠。不以登记日、出货日或下一次出租日冒充回收日。仍在出租不填写实际回收日，服务端拒绝该状态携带回收日。

已结束关系保留有效交付，不占用产品，不修改现存其他订单关系、当前配置或作业状态，不补造正常受付/回收作业。历史实际回收日与登记人、登记时间独立。仍在出租出现其他有效关联时阻止整单提交并保留输入；提醒弹窗显示产品/关联订单，并引导更正编号、如实改为已结束，或先经受付及作业管理完成原关系回收。错误原关联沿订单解绑处理，不强制覆盖。

### 8.2 首次基准及顺序

不能将首次登记订单自动视为真正首次。新建无基准产品仍须确认真实首次具体日；人员知道更早首次时必须填写，不用本单日冒充。后补更早有效交付时，核对已有来源及真实首次事实，确认后同事务更新首次日、基准月和有效来源，保留调整前后值、依据、登记人及时间。更晚交付不变更基准；同日不自动替换来源；已有更早外部依据则保留。来源半缺、事实矛盾不按简单MIN自动修复。

已结束的早期出租可早于系统当前出租，不应用旧“不得早于最近出租”的统一校验。仅按8.1校验本行日期，不校验跨订单历史期间重叠。更新首次依据不覆盖当前关联、名称、规格、部件配置或原订单快照。

### 8.3 通知与历史质检

新生命周期候选按更新后的基准计算；既有通知不阻止人工再次生成，同一提交重试仍防重。旧通知、PDF及受付跟踪保持原事实，不视为新周期已完成；不自动生成、重发或补发漏期。基准变化可能改变年次/月/通知类型或使其超出候选范围，不自动报废。确认时提示已有通知可能采用旧基准。

真实质检日期、确认人及时间保持不变。历史认定日期明确显示为“历史合格认定依据日”，创建时采用当时确认的真实首次日期，后来基准前移不重写该认定、不新增第二次质检、不改变合法通过标记。认定依据日与最新首次日期不再相等本身不算标记/事实矛盾；保留原认定依据和基准调整履历。真实质检事实与更早交付明显矛盾仍提示核对，不据日期强行通过。

### 8.4 最终确认、编辑与不可撤销

提交前统一二次确认订单号、产品/出货日、出租情况及已结束产品必填实际回收日；有基准变更时展示前后日期/月及已有通知影响。明确保存后无整笔撤销或级联删除。该确认不是合格确认勾选，不引入审批或草稿；返回修改保留输入，变更后重新确认，服务端仍锁后重验。

历史订单复用现有订单编辑页：允许纠正原订单号、受注日、三个客户角色及地址、备注；受注日沿日期校验，晚于出货日在同一次保存确认中提示。客户订单号、预计发货日等一般资料沿原规则。订单类型、产品明细、数量、历史出货/回收日、部件及质检事实不可普通编辑；首次基准只按更早有效交付规则调整。禁止删除、取消及撤销补录。当前错误关系沿订单解绑，实际回收沿受付与作业管理；解绑不删除历史依据。历史订单禁止新增正常发货，即使解绑使有效履约数量下降也不重新开放发货，后续新业务建立正常订单。既有通知和交付快照不回写。

### 8.5 最小交互及来源实现边界

提交前仅一个统一确认弹窗，集中展示产品、日期、出租状态、基准调整、日期异常及不可撤销说明；不额外逐项弹窗。未知结果仅在当前页面查询原请求或原样重试；离开后不承诺恢复，无法确认时人工核对，不自动重建。无跨页store、持久草稿或后台轮询。外部首次依据采用专用小型事实表，仅服务首次基准，保存产品、首次日期、登记来源、人和时间；不建设通用凭证平台。提交仅校验本次采用资料、首次依据及当前关系，不复制比较整个产品、不扫描全部历史、不识别相似旧单。
