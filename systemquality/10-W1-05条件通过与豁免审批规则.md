# W1-05 条件通过与豁免审批规则

> 状态：已确认  
> 决策日期：2026-11-23  
> 责任人：贾婉月（质量负责人）  
> 发布例外共同确认人：李旸（发布/运维或 SRE 负责人）  
> 登记入口：`exception-register.csv`  
> 每条变更内的证据副本：`evidence/<变更号>/exceptions.json`

## 1. 三个概念不能混用

| 类型 | 定义 | 是否改变门禁原始结果 | 最长期限 | 责任人 |
|---|---|---|---|---|
| 条件通过 | 检查已执行且有失败项，但在明确残余风险、补偿控制、回滚条件下允许进入下一步 | 否，原始失败必须保留 | P1 最长 24 小时或下一次复验；P2 最长 72 小时 | 门禁责任人 + 质量负责人 |
| 豁免 | 特定检查因客观原因不执行，允许用替代证据覆盖 | 否，必须显示“未执行” | 最长 10 个工作日，到期自动恢复阻断 | 门禁责任人 + 质量负责人 |
| 系统降级 | 工具、环境或规则整体不可用，切换到 D1-D4 保留核心验证 | 否，必须记录降级状态 | 每 24 小时复核 | 质量负责人提出，李旸确认发布影响 |

条件通过和豁免都不能把失败结果改成通过，也不能删除原始日志。最终报告必须同时显示“原始结果”和“例外处理结果”。

## 2. 禁止例外

以下情况不设条件通过或豁免，只能修复、回滚、隔离或延期发布：

- P0 安全问题、认证绕过、越权访问、敏感数据泄露。
- Secret、Token、密码或生产凭据进入版本库或证据包。
- 可导致订单、寄送、面单数据不可恢复损坏的缺陷。
- 无备份、无回滚或未验证回滚的破坏性数据库迁移。
- 核心订单到寄送链路的 P0 业务证据缺失且无法用其他确定性证据替代。
- 发布包无法绑定提交号、制品摘要或环境指纹。
- 明知道具错误仍将 AI 结论作为唯一通过依据。

安全类 P1 不允许“豁免不执行”，只能在补偿控制、回滚触发和人工监控均具备时申请条件通过。

## 3. 分级审批矩阵

| 等级与范围 | 允许类型 | 必需审批人 | 最长期限 | 强制条件 |
|---|---|---|---|---|
| P0 任意范围 | 不允许 | 无 | 不适用 | 修复、回滚或延期 |
| P1 安全、权限、数据一致性 | 仅条件通过 | 张树旸（安全）、贾婉月（质量）、李旸（发布） | 24 小时或下一次复验，以先到者为准 | 补偿控制、监控、回滚触发、指定复验时间 |
| P1 非安全业务或质量 | 条件通过或豁免 | 贾婉月（质量）、李旸（发布） | 72 小时 | 业务负责人确认残余风险，保留替代证据 |
| P2 安全相关 | 仅条件通过 | 张树旸、贾婉月、李旸 | 24 小时 | 安全补偿控制和复验 |
| P2 一般质量 | 条件通过或豁免 | 贾婉月、对应门禁责任人 | 10 个工作日 | 保留替代证据和复验计划 |
| G5 发布相关任意例外 | 条件通过或豁免 | 李旸、贾婉月；安全项另加张树旸 | 按对应等级上限 | 明确灰度、监控和回滚责任 |

补充约束：

1. 执行人不能审批自己提交的例外。
2. 张树旸作为开发执行人时，G2 例外必须由贾婉月复核。
3. G3/G4 例外必须由贾婉月和李旸共同确认，防止质量负责人兼订单链路负责人时缺少独立复核。
4. G5 最终发布确认只能由李旸完成，张树旸和贾婉月均不能替代。
5. 审批通过不等于风险关闭；到期必须重新验证，未复验自动转为阻断。

## 4. 申请前置条件

任何例外申请必须同时具备以下字段，缺一项即退回：

| 字段 | 要求 |
|---|---|
| `exception_id` | 全局唯一，格式 `EX-YYYYMMDD-序号` |
| `change_id` | 对应变更号 |
| `commit_sha` | 被测提交号，不得使用分支名替代 |
| `gate_id` | G0-G5 |
| `check_id` | 具体失败检查名称 |
| `severity` | P0/P1/P2 |
| `exception_type` | `conditional-pass` 或 `waiver` |
| `reason` | 客观原因，不接受“时间不够”作为唯一理由 |
| `business_impact` | 对订单、寄送、面单、权限或数据的具体影响 |
| `compensating_control` | 人工检查、监控、灰度、开关或回滚措施 |
| `revalidation_plan` | 复验命令、负责人和时间 |
| `owner` | 例外关闭责任人 |
| `approved_by` | 审批人姓名和角色 |
| `expires_at` | 绝对时间，不允许只写“下周” |
| `rollback_trigger` | 出现何种现象立即回滚 |
| `evidence_path` | 证据包内路径 |

## 5. 生命周期

1. 申请：开发或平台负责人创建例外记录，附原始失败证据。
2. 初审：质量负责人检查等级、补偿控制和复验计划。
3. 审批：按矩阵完成多人审批；安全项必须有张树旸，发布影响必须有李旸。
4. 执行：门禁结果标记为 `conditional` 或 `waived`，原始失败仍保留。
5. 监控：例外期间按声明的监控和回滚触发执行。
6. 复验：到期前重新运行检查，记录通过、失败或升级。
7. 关闭：通过则关闭例外并保留历史；失败则恢复阻断或回滚。
8. 周复盘：统计例外率、到期未关闭数、因例外导致的逃逸缺陷。

## 6. 自动失效与升级

| 条件 | 自动动作 |
|---|---|
| 到达 `expires_at` | 例外失效，门禁恢复阻断 |
| 检查连续失败两次 | 条件通过升级为阻断 |
| 出现 P0/P1 缺陷或线上逃逸 | 立即关闭相关例外并进入复盘 |
| 环境指纹或提交号变化 | 例外失效，需重新申请 |
| 模型、提示词或工具版本变化 | AI 相关例外失效 |
| 例外率高于 5% | 进入 D1 观察并专题复盘 |

## 7. 维护方式

- 贾婉月负责 `exception-register.csv` 的最终完整性和周度复核。
- 每个变更的执行人负责补充变更内 `exceptions.json`，但不得自行审批。
- 李旸负责发布相关的到期和回滚确认。
- 张树旸负责安全项的补偿控制和复验技术证据。
- 每周复盘只更新实际状态，不删除历史行；过期记录保留并标记为 `expired` 或 `closed`。
