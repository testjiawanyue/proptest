## 1. 设计原则

Oracle 不是“页面能打开”或“接口返回 200”，而是业务必须成立的最小事实。每条 Oracle 至少需要一个正向证据和一个反例或边界证据，并明确页面、接口、数据库或文件中的可比对字段。

AUTO 测试数据必须带唯一前缀，执行后按登记范围清理；不得依赖全库清空脚本。账号凭据只登记受控位置，不在本文件写明文。

## 2. 首批 Oracle

### ORD-STATE-01 寄送确认后的状态与事实一致

**业务事实**：一笔处于 `preparing` 的寄送完成确认后，寄送状态变为 `shipped`，确认人和确认时间被记录；订单仍为有效状态，相关产品形成当前有效的订单关系，产品首次寄送事实被采用。

**前置条件**：

- 订单状态为 `active`，剩余可寄送数量大于 0。
- 寄送状态为 `preparing`，至少加入一个可寄送产品。
- 已填写承运商和寄送日期，收货地址校验通过。

**动作**：调用 `POST /prop/shipment/{shipmentId}/confirm` 并重复调用一次验证幂等。

**必须断言**：

| 证据层 | 断言 |
|---|---|
| API | 第一次确认 `code=200`，返回寄送 `status=shipped`；重复确认仍返回成功且不产生第二组关系 |
| 数据库 | `prop_shipment.status=shipped`；`confirmed_by`、`confirmed_time` 非空 |
| 数据库 | `prop_order.order_status=active`（取消场景除外） |
| 数据库 | 每个寄送产品存在唯一 `prop_product_order_relation`，`delivery_valid=1` |
| 数据库 | `prop_product_order_relation.shipment_id`、`shipment_product_id` 与寄送记录一致 |
| 数据库 | `prop_shipment_reservation` 中对应产品占用已释放 |
| 数据库 | 产品 `first_shipment_date`、`lifecycle_base_month`、`baseline_shipment_id` 已采用本次寄送事实 |
| UI | 订单详情寄送履历显示已寄送状态，确认后不再出现可重复确认入口 |
| 文件 | 确认同时生成 `file_type=mail` 的版本化文件记录 |

**失败分类**：`business/state`、`data/consistency`、`idempotency`。

### ORD-DATA-01 寄送产品数量与订单剩余数量一致

**业务事实**：寄送产品行数不得超过订单剩余可寄送数量；确认后订单关系数量与寄送产品数量一致，未寄送产品不能产生寄出关系。

**前置条件**：创建数量为 2 的测试订单，准备两个不同产品。

**动作**：分别验证只加入 1 个产品、加入 2 个产品和尝试加入第 3 个产品的结果。

**必须断言**：

- 加入 1 个产品后寄送产品数为 1，订单已履行数量仍为 0。
- 加入 2 个产品后寄送产品数为 2，订单剩余数量为 0。
- 尝试加入第 3 个产品被拒绝，失败原因属于数量超限，且数据库无新增寄送产品。
- 确认后关系数为 2，关系中的产品集合等于寄送产品集合。
- 任何未被本次寄送包含的产品不得出现本次 `shipment_id` 的有效关系。
- 页面寄送产品行数、API `products` 数量和数据库聚合三者一致。

**失败分类**：`business/quantity`、`data/consistency`、`transaction`。

### ORD-FILE-01 寄送通知与面单文件可追溯

**业务事实**：寄送确认生成的通知邮件记录和面单文件必须能追溯到寄送号、请求标识、模板版本和内容快照；文件版本单调递增且同一请求幂等。

**前置条件**：使用 `ORD-STATE-01` 已确认的寄送；承运商选择 Yamato 或 Sagawa 的受控测试配置。

**动作**：

1. 读取确认生成的 `mail` 文件。
2. 通过受控批量面单接口生成 `waybill` 文件。
3. 使用相同请求标识重复提交。
4. 下载或读取文件内容并核对格式。

**必须断言**：

- `prop_shipment_file.shipment_id` 与寄送号一致。
- `file_type` 为 `mail` 或 `waybill`，且请求标识唯一。
- `version` 从 1 开始递增，无重复版本。
- `template_version`、`request_id`、`payload_hash` 非空。
- 相同请求标识重复提交返回同一文件记录，不新增版本。
- `snapshot_json` 中的承运商、寄送号、产品集合与数据库一致。
- `waybill` 输出为可打开的 XLSX；`mail` 输出为可读取的文本/结构化内容。
- 文件名、页数/工作表数、关键收件人与承运商字段与快照一致。

**失败分类**：`file/generation`、`file/version`、`idempotency`、`data/consistency`。

### ORD-AUTH-01 无权限用户不能查看或操作寄送

**业务事实**：未登录用户不能读取寄送；已登录但无 `prop:order:page` 和 `prop:orderBatchPrint:page` 权限的用户不能查看、修改或确认寄送。

**前置条件**：使用受控角色矩阵中的管理员、普通有权限用户、无权限用户；凭据只登记在受控凭据库。

**动作**：

- 未登录请求 `GET /prop/shipment/{id}`。
- 无权限用户请求 `GET`、`POST`、`PUT`、`DELETE` 和 `confirm`。
- 有查看权限但无写权限的用户尝试修改和确认。

**必须断言**：

- 未登录返回认证失败，不返回寄送正文。
- 无权限用户返回 401/403 或统一权限错误，响应中不包含寄送详情。
- 有查看权限但无写权限的用户不能修改、删除或确认。
- 页面隐藏或禁用无权操作入口，且不能仅靠前端隐藏实现安全控制。
- 被拒绝的请求没有产生寄送、产品、关系、文件或状态变化。

**失败分类**：`security/authz`、`security/data-exposure`、`audit`。

## 4. 执行顺序

1. `ORD-AUTH-01`：先确认权限边界，避免后续写操作越权。
2. `ORD-DATA-01`：准备受控订单和产品，验证数量与事务。
3. `ORD-STATE-01`：确认寄送并验证状态、关系、产品和幂等。
4. `ORD-FILE-01`：基于已确认寄送验证邮件、面单和版本。

## 5. 不通过时的处理

- 状态或关系错误：P1 业务/数据风险，G4 阻断，禁止继续生成文件。
- 数量不一致：P1 数据一致性风险，恢复全量核心回归并检查事务边界。
- 文件无法追溯或版本重复：P1 文件风险，停止发布并保留原始产物。
- 权限绕过或数据泄露：按 P0/P1 安全规则处理，不允许豁免。
- 未确认项：标记 `unconfirmed`，由贾婉月和张树旸人工裁定，不得自动通过。
