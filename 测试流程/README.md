# 测试验证流程 v3.0（项目外需求基准 + 三方对齐 + 人工把控问题点）

> **流程定位：代码提测时的「验证与回归」测试流程**。覆盖"提测模块 → 按外部 spec 验证 → 三方对齐找缺口/缺陷 → 人工裁定问题点 → 发开发/改用例 → 回归复验关闭"；**不含**需求定稿、上线发布放行授权（那部分另立单版本发布确认）。
>
> 生效：2026-11-13　唯一流程入口
> 变更原因：v2.0 把审核基准误收敛到**项目内** `prop_new/docs/spec`（开发自带文件，等于"自己证明自己"，黑盒），且删掉了人工把控环节。本版纠正两点：
> 1. 需求审核基准改回**项目外的独立需求文档 `E:\proptest\spec`**；
> 2. 恢复**人在"问题点裁定"上的把关**，并把你原有的「需求↔用例对齐 / 三方对齐 / 问题点自动验证」资产接回主线。

## 一、四个真实资产（全部在项目外，构成验证链）

| 资产 | 路径 | 在流程中的角色 |
|---|---|---|
| **需求基准（审核标准）** | `E:\proptest\spec`（spec9-29 / spec10-28 最新 / 变更分析 / 业务梳理 / 风险评估） | 唯一需求审核依据，独立于开发项目。开发项目内 `prop_new/docs/spec` **仅作代码侧交叉参考**，不当审核基准 |
| **测试用例点** | `E:\proptest\case\outputs\测试用例汇总\测试用例汇总_V5.xlsx`（T03 修复后 1257 条唯一用例）/ 各模块测试用例 md | 测试侧对需求的"验证点"表达 |
| **三方对齐验证工作台** | `E:\proptest\ai-test`（01-requirement / 02-code / 03-testcase / 04-validation / 05-report；提示词 T01~T08） | Spec↔Code↔Test 三条证据链两两比对 + 三方交叉，产出覆盖矩阵与 P0~P3 问题分级 |
| **问题点自动化验证 + 问题登记** | `E:\proptest\auto-explore`（Playwright+Agent 自动探索 + `测试问题记录.md` 统一登记） | 对问题点跑自动化验证；问题统一登记并带**人工裁定**与防重复规则 |

> **为什么不用项目内 `prop_new/docs/spec` 当基准**：它是开发项目自带文件，用它与代码互证缺少独立外部核验，正是你指的"黑盒"。外部 `spec/` 由测试/需求侧独立维护并带版本差异（`spec10-28-vs-spec9-29-变更分析.md`），才是审核基准；开发项目内那份只用于"开发是否按外部 spec 实现"的交叉对照（即 ai-test T04 的对象）。

## 二、一个模块的验证闭环（5 阶段，人参与把控）

```
S0 需求文档审核        取 spec10-28 为基准 + 变更分析 + 业务梳理/风险 → 模块 REQ 基线（ai-test/01）
        ↓
S1 需求↔用例点对齐      spec 的 REQ 点 对 case/V5 用例点（T05 覆盖矩阵 FULL/PARTIAL/MISSING）→ 缺口清单
        ↓
S2 三方对齐验证(按完成模块)  ai-test T02代码行为 + T04 Spec→Code + T06 Code→Test + T07交叉(P0~P3)
        ★ 强制：所有 FULL/PARTIAL/MISSING/冲突 结论必须回到【当前 prop_new 代码】重新核对，不能只信 ai-test 历史对齐文档（见 §九，已发现过期误判）
        ↓
S3 问题点识别 + 人工把控 ★ 所有缺口/失败汇入 auto-explore/测试问题记录.md，人逐条裁定：
        真实缺陷(发开发) / 需求偏差(改spec或用例) / 环境问题(不修) / 待定 / 不修改(产品确认)
        ↓  ★ 只有"裁定=真实缺陷"才进发开发清单；这一步必须有人，不能自动过
S4 问题点自动化验证     auto-explore 三路探针跑自动化验证，结果回写登记（状态流转 + 防重复）
        ↓
S5 发开发(飞书登记) + 回归复验    已裁定真实缺陷 → 直接登记飞书多维表格（与开发沟通的唯一渠道：描述含现象/spec依据/修复建议/代码证据）；**测试侧不拟修复SQL、不复验造数脚本**，开发见飞书记录自行修复；下次拉代码回归已验模块 + 逐条复验"待验收"问题 → 关闭
        ↓   ★ 一个模块闭环到此
```

> **S2 代码复核对齐（流程补强，来自 masterdata 试点体检）**：`ai-test` 的 T04/T06 三方对齐文档写于 2026-10-12，相对当前 `prop_new` 代码**会过期**（试点中其"部件资料-017 无唯一性检查"结论，已与当前代码 `requireUniqueName` 拦截重名不符）。因此 S2 的任何 FULL/PARTIAL/MISSING/冲突 结论，**进 S3 前必须由人回到当前 `prop_new` 代码 re-check**（读 Service / Mapper / 实际行为），不能只信历史对齐文档。S2 的产出只是"待 S3 裁定的候选清单"，不是最终结论。

## 三、人在哪几个点把关（明确的人工控制闸）

| # | 把关点 | 谁 | 动作 |

| 1 | 需求基线版本 | 测试 / 需求 | 确认以 spec10-28 为当前标准，识别与 spec9-29 差异 |

## 九、试点体检与流程补强（来自 customer / masterdata 两个试点）

两个试点各跑通一次 S0~S5，验证"读 spec → 对齐 → 三方验证 → 人工裁定 → 改 xlsx → 发开发/关跟踪"链路可落地，同时暴露并固化了以下流程规则：

| # | 发现 | 已固化为流程规则 | 出处 |
|---|---|---|---|
| 1 | `ai-test` 的 T04/T06 三方对齐文档（2026-10-12）相对当前 `prop_new` 代码会过期，其"部件资料-017 无重名检查"结论与当前代码 `requireUniqueName` 拦截重名已不符 | **S2 强制"回到当前 `prop_new` 代码 re-check"**，S2 产出只是"待 S3 裁定的候选"，不是结论（见 §二流程图注 + 本文件 §二下方提示） | masterdata 试点 |
| 2 | S3 人工闸会拦住"实测看似冲突、但 spec 沉默 / 代码已实现"的伪缺陷（如 B-2 并发静默覆盖、B-1 重名已拦）。若只信 V5 实测或只信 ai-test 文档，都会被误发开发当缺陷 | **S3 裁定必须同时查"外部 spec 要求 + 当前代码实现"**，两者任一不支持"缺陷"判定的，归为非缺陷（改用例 / 不修改） | customer + masterdata 试点 |
| 3 | 说的"改用例"必须**打开 `测试用例汇总_V5.xlsx` 实际改行**，不能只出文档记录。试点发现 6 条"待回写"里 5 条 2026-10 已改好，漏网 1 条（customer 的 A-2）和 masterdata 的 B-1/B-2 才需实际改 | **裁定=需求偏差/非缺陷且涉及用例口径的，当场改 xlsx 并存备份**（命名 `_backup_YYYYMMDD_before_*.xlsx`） | 两个试点 |
| 4 | 已裁定真实缺陷"发开发"时，容易滑向"测试侧再拟一份修复 SQL + 复验造数脚本给开发"的多余环节 | **S5 = 直接登记飞书多维表格（与开发沟通的唯一渠道）**：描述含现象 + spec 依据 + 修复建议 + 代码证据行号即可；测试侧**不拟修复 SQL、不复验造数脚本**，开发见飞书记录自行修复，测试侧只负责"登记 + 后续复验关闭" | FEAT-00 试点（DASH-001/002 已按此落地） |

> 四个规则都已落地执行：customer 试点改了 A-2（行级实际改），masterdata 试点改了 B-1（行18）/ B-2（行24），均带备份；FEAT-00 试点把 DASH-001/002 直接登记飞书（reczz28Z7k6W5j3H / reczz28Z7kA9LZWB）作为与开发沟通渠道，未另拟 SQL/造数脚本；所有改动同步登记进 `auto-explore/测试问题记录.md` 的批次索引与 §4.2 复核结论，防重复报。
