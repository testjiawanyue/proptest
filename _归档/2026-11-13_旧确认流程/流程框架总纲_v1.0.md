## 3. 发布门禁规则（L3）

### 3.1 版本清单（每次发布必填）

发布前必须填一张 `releases/REL-{版本}/manifest.md`（模板：`templates/发布清单_模板.md`），内容包括：

| 项 | 说明 |
|---|---|
| 版本号 / commit / 日期 | 冻结的基线与产物可追溯 |
| **本版本包含的模块** | 只列真正交付给客户的，不是"主干上有的" |
| 每个模块的准出状态 | 直接抄台账，不重新判定 |
| 未包含但代码已在主干的模块 | 必须列，用于评估"带病上线"风险 |
| 数据库迁移清单 | 有无不可逆 DDL |
| 已知残余风险 | 从各卡 `条件通过` 汇总 |

### 3.2 四类硬条件（缺一即阻断）

| # | 硬条件 | 判定依据 | 例外 |
|---|---|---|---|
| 1 | 本版本包含的模块，`04-准出卡` 结论均非 `阻断` | `modules/*/04-准出卡.md` | 无 |
| 2 | **X1 / X2 / X4 三张卡判定为 `通过`** | `specials/X{1,2,4}*.md` §4 | 无（不允许条件通过） |
| 3 | P0 / P1 缺陷遗留 = 0；P2 有书面接受（责任人 + 影响范围） | 飞书缺陷台账 | 无 |
| 4 | 自动化新增失败 = 0（相对冻结基线）；flake 已定性 | 本轮执行结果 vs 基线 | 无 |

**非硬条件的部分**（可条件通过，但须进放行报告）：

- X3 / X5 / X6 判定为 `条件通过`；
- 本版本未包含、但代码已在主干的模块（"带病上线"）；
- 任何 `【待确认】` 事项。

### 3.3 三档结论

| 结论 | 条件 | 谁签 |
|---|---|---|
| **放行** | 四类硬条件全过，无非硬条件遗留 | 测试负责人 |
| **条件放行** | 四类硬条件全过，但存在非硬条件遗留 | 测试负责人 + **产品**（须写明接受理由与影响范围） |
| **阻断** | 任一硬条件不满足 | 测试负责人，开发负责人知会 |

**纪律**：`条件放行` 同一产品线累计 **2 次** → 下一版本强制 `阻断`，不接受协商。这条是为了防止"条件放行"变成常态。

### 3.4 产出

| 产出 | 路径 | 谁写 |
|---|---|---|
| 版本清单 | `releases/REL-{版本}/manifest.md` | 测试 |
| 交叉验证报告 | `ai-test/04-validation/cross-validation.md` | 测试（当前是空文件，必须填） |
| 放行报告 | `ai-test/05-report/ai-validation-report.md` | 测试（当前是空文件，必须填） |

> 这两个空文件是当前最大的管理风险：门禁写了却没人产出结论，等于没有门禁。

## 4. 角色与权责（谁必须签字）

| 角色 | 必须确认什么 | 在哪份文件 | 不签的后果 |
|---|---|---|---|
| **产品** | P0 VP 的优先级定级 | `01` §4.1 | 重点测偏 |
| **产品** | 裁决变更清单（用例与最新裁决冲突时） | `01` §5 / `02` §0.2 | 用过期规则判定，结论整体失真 |
| **产品** | 条件放行的接受理由 | `releases/REL-XX/manifest.md` | 风险无人承担，等于免死金牌 |
| **开发** | 表名、change 完成度（实测值） | `00` §1.1 / §1.2 | DB 验证无效（已实测踩过） |
| **开发** | 每个 P0 VP"是否已编码" | `01` §4.2 | **R-09 陷阱**：把未实现判成通过 |
| **开发** | 缺陷认领与修复 | 飞书缺陷台账 | 缺陷无人管 |
| **测试** | 全部执行与证据 | `03` | — |
| **测试负责人** | 模块准出结论、发布结论 | `04` §6 / 放行报告 | 无条件准出 |

**一句话**：产品管"什么最重要"，开发管"做没做"，测试管"测没测到"。三者缺一，门禁就是自证清白。

## 5. 状态机与变更权限

### 5.1 模块状态

```
待接入 → 文档就绪 → 验证中 → 待准出 → 已准出 → 回归基线
                  ↓                              ↑
                阻断 ────────────────────────────┘（修复后回 验证中）
                  ↓
              条件准出（带残余风险入池）
```

### 5.2 谁能改状态（**口头变更一律无效**）

| 状态变更 | 有权人 | 前置条件 |
|---|---|---|
| `待接入 → 文档就绪` | 测试 | `check-module.mjs --gate=M1` 退出码 0 |
| `文档就绪 → 验证中` | 测试 | M1 通过 + 台账填了执行人 |
| `验证中 → 待准出` | 测试 | M2 通过 + `03` 有执行证据 |
| `待准出 → 已准出` | **测试负责人** | M3 通过 + 三签齐 |
| `待准出 → 条件准出` | **测试负责人 + 产品** | 产品在 `04` 签字写明接受理由 |
| `→ 阻断` | 测试 | 无需审批（宁可错杀） |
| `已准出 → 回归基线` | 测试 | 已登记进 `回归基线池.md` |

**所有变更当日更新台账并填日期**，历史状态不覆盖。

## 6. 基线池规则

`已准出` 的模块必须登记进 `回归基线池.md`，否则不算入池。规则：

| 项 | 内容 |
|---|---|
| 入池条件 | 模块状态 = `已准出`，且 A 类用例已有自动化并通过 |
| smoke 范围 | 入池模块的 P0 验收点对应自动化，单轮 ≤ 10 分钟 |
| 执行时点 | **每个新模块 S0 之前必须跑一次**；发布前必跑一次 |
| 维护人 | 测试 |
| 出池条件 | 该模块被回退或重大改版 |

这条是分批交付下唯一能防"最后集成十连爆"的机制。

## 9. 规则修订机制

| 触发条件 | 动作 |
|---|---|
| 同一类问题在 2 个以上模块重复出现 | 修订模板，升小版本 |
| C 阶段累计发现 3 个新坑 | SOP 升 v1.2 |
| 硬条件被绕过 1 次 | 立即收紧规则，不等到累计 |
| 发布门连续 2 次条件放行 | 强制阻断一次，复盘原因 |

**修订须记录版本号与变更依据**，不接受"口头改了"。
