## 1. A～E 分类规则（打标依据，不是主观判断）

| 类 | 判定条件 | 执行策略 |
|---|---|---|
| **A** | 覆盖 P0 验收点，或关联高风险编号 | **100% 执行**，优先自动化 |
| **B** | 覆盖 P1 验收点的主流程 | 自动化覆盖 + 人工抽检 20% |
| **C** | 覆盖仅本 change 涉及的验收点 | 跟随 change 验收，change 归档后转 B |
| **D** | 显示 / 文案 / 排序 / 布局类 | 合并为模块检查单，人工走查，不逐条执行 |
| **E** | 重复、与当前代码冲突、需求已过期、无法执行 | **归档或作废**，不计入分母 |

> 打标后本模块的"待执行分母"= A + B×20% + C。这个数字才是执行率的分母。
> **裁决冲突的用例一律归 E 类**（已过期），并登记 D 编号——不要留着当 A/B 类跑，否则测的是旧规则。

## 3. 验收点覆盖矩阵（反向检查，防止有 VP 没人测）

> **v1.1 重大变更（坑 4）**：原"是否有自动化"只有"是/否"，会把"有测试文件但从未跑绿"当成"已覆盖"。
> 现在改为**四态**，M1 门只认 `已通过`，其余三态按缺口对待。

| VP 编号 | 优先级 | 覆盖它的用例 | 自动化状态 | 证据（脚本 / 最近执行记录） |
|---|---|---|---|---|
| VP-XX-001 | P0 | 部件资料-001 | **已通过** | `PropXxxTest` 2026-11-xx 全绿 |
| VP-XX-002 | P0 | 部件资料-002 | **已存在未跑** | `webauto/.../test_xx.py`，无近期执行记录 |
| VP-XX-003 | P0 | 部件资料-003 | **失败** | `PropYyyTest` 133 error（模板校验和） |
| VP-XX-004 | P0 | **无** | **缺口** | — |
| | | | | |

**自动化状态定义（口径必须统一）：**

| 状态 | 定义 | M1 门认不认 |
|---|---|---|
| `已通过` | 近期（本模块验证周期内）实际跑过且全绿，有结果文件/时间戳可查 | ✅ 认 |
| `已存在未跑` | 有脚本/测试类，但本轮没跑，或无执行记录可证 | ❌ 按缺口 |
| `失败` | 跑过但有失败/错误 | ❌ 按缺口，且属阻断级 |
| `缺口` | 完全没有对应自动化 | ❌ 按缺口 |

> **每个 P0 的 VP 必须至少被一条用例覆盖，且其自动化状态为 `已通过` 或明确接受"人工验证"**。
> 出现"无"或"已存在未跑"即 M1 门不通过。这是最有效的拦截点。
