## 三、门禁自检（v1.1 新增）

```bash
# 单模块，全部三道门
node tools/check-module.mjs modules/FEAT-02-part-profile

# 只查文档门
node tools/check-module.mjs modules/FEAT-02-part-profile --gate=M1

# 扫描全部模块（汇总各模块 FAIL 数）
node tools/check-module.mjs modules/ --all

# 机读输出（供后续接 CI）
node tools/check-module.mjs modules/xxx --json
```

**退出码**：有 FAIL → 1，否则 0。可直接用于 CI 门禁。

**脚本会拦什么（对应 7 个坑）：**

| 检查项 | 拦什么 | 对应坑 |
|---|---|---|
| M1-01 | 模块卡表名无实测证据来源 | 坑 3 |
| M1-02 | change 名无实测日期 | 坑 2 |
| M1-11/12 | 无裁决基线 commit、无 VAL 枚举 | 坑 1、坑 7 |
| M1-13 | VP 状态为空、未定级 | — |
| M1-14 | P0 VP 未经产品/开发确认 | 坑 6 |
| M1-21 | 未导出 V5 用例 | 坑 7 |
| M1-24 | **P0 的自动化状态不是「已通过」** | 坑 4 |
| M2-02/03 | 自动化无执行时间戳、依赖层有失败 | 坑 5 |
| M3-03 | 自动化健康度有失败仍想准出 | 坑 5 |
| M3-06 | G-M3 硬条件为「否」 | 坑 4/5/7 |

## 四、五条填写纪律（比 v1.0 多两条）

1. **01 必须重新编号**。不要沿用 `validation.md` 的 VAL 序号——原文会随迭代变化，VP 编号必须稳定。
2. **02 的覆盖矩阵必须逐行填**，出现"无"就说明有验收点没人测。这是整个流程最有效的拦截点。
3. **03 只追加不修改**。每轮一条记录，历史轮次永不覆盖，否则失去审计性。
4. **🆕 先说清"对的是哪一版裁决"**。`01 §0` 必须填 `validation.md` 的最后修改 commit。不填，后面所有对账都没有锚点（坑 7）。
5. **🆕 "有自动化"不算覆盖，只有"已通过"才算**。四态：`已通过` / `已存在未跑` / `失败` / `缺口`；M1 只认第一种（坑 4）。

## 六、样板暴露的真实问题（v1.1 复核后）

`modules/FEAT-02-part-profile/` 走完 v1.1 后，门禁结论是**阻断**，原因写得很具体：

- 7 个 P0 VP 的自动化状态全是「缺口」或「失败」，**A 类自动化率 0%**；
- `部件资料-013` 依据旧裁决（衣体空前缀可保存）判"通过"，新裁决已改为拒绝 → **D-02-01**；
- V5 47 条**执行率 100%**，但"执行过"不等于"结论有效"。

> ⚠️ 这里要特别说明：**执行率高不等于质量好**。47 条里 45 条判通过，但至少 1 条的通过依据已经失效。
> 这种"看起来有证据、实际不成立"的情况，比"从没测过"更难发现——这也正是 v1.1 要加 §0 裁决基线的原因。
