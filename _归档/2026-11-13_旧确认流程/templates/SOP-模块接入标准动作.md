# 模块接入标准作业流程（SOP）v1.1

> 用途：把"每个模块怎么接入测试门禁"从**口口相传**变成**照着做的清单**。
> 适用：FEAT-02 之后的所有模块（含 C 阶段批量接入）。
> 依据：B 阶段试点暴露的 7 个坑（见 `modules/B阶段踩坑记录.md`）。
> 一句话：**每模块 8 步，3 道门，1 个自检脚本。不按顺序做，门禁就是空转。**

---

## 一、总览

```
S0 立项 ──> S1 模块卡 ──> S2 验收点 ──> S3 V5导出+对账 ──> S4 用例归属
                                                              │
                          ┌───────────────────────────────────┘
                          ▼
                    ■ G-M1 文档门（脚本自检 must pass）
                          │
                          ▼
                    S5 执行验证 ──> ■ G-M2 执行门（证据齐 + 依赖层全绿）
                          │
                          ▼
                    S6 准出卡 ──> ■ G-M3 准出门（12 项检查）
                          │
                          ▼
                    S7 入基线池 + 登记 suite + 跑 smoke
```

**角色分工（必须落实到人，不能"测试全包"）：**

| 步骤 | 主责 | 配合 | 为什么不能一个人做 |
|---|---|---|---|
| S1 模块卡 | 测试 | 开发（接口/表名/change） | 表名和 change 靠猜必错（坑 2/3） |
| S2 验收点 | 测试 | **产品**（定优先级）、**开发**（是否已编码） | VP 拆错会让后面全错（坑 6） |
| S3 V5 导出对账 | 测试 | 产品（裁决定论） | 用例过期需业务方拍板（坑 7） |
| S4 用例归属 | 测试 + 自动化 | 开发（脚本路径） | — |
| S5 执行 | 测试 / 自动化 | 开发（修缺陷） | — |
| S6 准出 | 测试负责人 | 产品（条件准出必签） | — |

## 二、逐步动作

### S0 立项（30 分钟）

| 项 | 动作 |
|---|---|
| 1 | 建目录 `modules/{FEAT-XX}-{slug}/` |
| 2 | 复制 `templates/` 下 5 份模板，重命名为 `00-模块卡.md` … `04-准出卡.md` |
| 3 | `模块接入台账.md` 对应行状态改 `验证中`，填责任人 |

**产出**：空目录 + 5 份待填文件
**卡点**：台账里没有这个模块 → 先补台账行，否则后面没人知道它存在

---

### S1 填 00-模块卡

**必须实测的两项（v1.1 硬要求）：**

```bash
# ① 表名实测（三选一，写出证据）
grep -rl "prop_your_table" prop_new/ruoyi-prop/src/main/resources --include="*.xml"
grep -rn "CREATE TABLE.*prop_xxx" prop_new/sql/

# ② change 实测（不许凭记忆）
cd prop_new/openspec/changes && for d in */; do d="${d%/}"; [ -f "$d/tasks.md" ] && \
  echo "$d: $(grep -c '^- \[x\]' "$d/tasks.md")/$(grep -c '^- \[' "$d/tasks.md")"; done
```

**自检点**：
- [ ] §1.1 每张表都有"证据来源"（文件:行号）
- [ ] §1.2 change 名来自实测目录，有实测日期
- [ ] §3 依赖表填了（这是回归触发的唯一依据）
- [ ] §4 风险标签从风险评估文档摘了，不是自创

---

### S2 填 01-验收点清单

**顺序不能反：先枚举 VAL，再拆 VP。**

```bash
cd prop_new/docs/spec/docs/features/{FEAT-XX}
grep -oP "VAL-[A-Z0-9]+[a-c]?" validation.md | sort -u | tr '\n' ' '
grep -oP "VAL-[A-Z0-9]+[a-c]?" validation.md | sort -u | wc -l
git log -1 --format=%h -- validation.md     # 裁决基线 commit
```

**三类异常必须先标注**（坑 1）：

| 类型 | 处理 |
|---|---|
| 空标题 | 不独立成 VP，注明 `VAL-xx(正文缺失)` |
| 指针/引用 | 合并到源 VP，注明"合并" |
| 跨段重复 | 拆两条，加 `-A`/`-B` 后缀 |

**VP 评审（坑 6，P0 必做）**：
- 产品：确认优先级（P0/P1/P2 定得对不对）
- 开发：确认"是否已编码 / 编码到什么程度"（**这条防 R-09 陷阱**）

**自检点**：
- [ ] §0 裁决基线 commit 已填
- [ ] VAL 枚举结果已粘贴，条数与总数一致
- [ ] 全部 P0 VP 在 §4.1 有产品确认、§4.2 有开发确认
- [ ] 验收点表无空状态、无空裁决来源

---

### S3 V5 导出 + 裁决对账（v1.1 新增，最容易跳过但最要命）

```bash
cd E:/proptest
python -c "
import openpyxl
wb=openpyxl.load_workbook('case/outputs/测试用例汇总/测试用例汇总_V5.xlsx',read_only=True,data_only=True)
print(wb.sheetnames)
"
# 按工作表导出本模块用例 → 02b-V5用例映射.md
```

**对账动作**：逐条比对"用例预期" vs "01 的裁决基线"。

- 对不上 → 登记到 `01 §5 裁决变更清单`（D 编号）+ `02 §0.2`
- 冲突用例一律归 **E 类**（作废），不许当 A/B 类跑
- 记录存量执行率：若为 0，在 02 §5 明确标注"此前未做过任何执行验证"

**为什么这一步不能省**：试点发现 `部件资料-013` 还写着"空前缀可保存"，而 10-31 裁决已改为"拒绝"。**按旧用例执行，测的是错的规则，准出结论整体失真。**

**自检点**：
- [ ] `02b-V5用例映射.md` 已生成，行数与导出数一致
- [ ] 对账表填了，冲突条数已登记 D 编号
- [ ] 存量执行率已填

### S4 填 02-用例与自动化归属

**核心变化：覆盖矩阵用四态（坑 4）**

| 状态 | 含义 | M1 认不认 |
|---|---|---|
| `已通过` | 近期跑过且全绿，有结果文件 | ✅ |
| `已存在未跑` | 有脚本但本轮没跑/无记录 | ❌ 按缺口 |
| `失败` | 跑过但有失败 | ❌ 阻断级 |
| `缺口` | 完全没有 | ❌ |

**自检点**：
- [ ] 无 P0 处于 `已存在未跑` / `失败` / `缺口`（或已在准出卡登记为例外）
- [ ] A 类自动化率按"仅计已通过"口径算
- [ ] 每个 `已通过` 都能指出执行时间 + 结果文件

### ■ G-M1 文档门（脚本自检）

```bash
node tools/check-module.mjs modules/{FEAT-XX}-{slug} --gate=M1
```

**通过条件**：S1～S4 全部自检点 PASS。
**不通过的典型原因**：表名靠猜、change 凭记忆、VP 没评审、V5 没导出。
**纪律**：**门禁不认"我口头确认过了"，只认文档里的实测记录。**

---

### S5 执行验证 + 填 03-验证记录

**先跑自动化拿证据，再填文档。顺序反了就是在编。**

```bash
# L0 后端
cd prop_new && mvn -pl ruoyi-prop test
# L0 前端
cd prop_new/ruoyi-ui && npm test
# L2 E2E
cd webauto/webtest && pytest tests/ -k <模块>
# L2' 脚本
cd auto-explore && npx tsx run-suite.ts --tag=module:<x>
```

**必须填 03 §0 自动化执行证据**（坑 5）：时间戳 + 结果文件 + 通过数。
**存量失败要单列**（如后端 133 error、前端 21 失败），并判断"是否影响本模块结论"。

**自检点**：
- [ ] §0 五行（L0后/L0前/L1/L2/L2'）都有时间戳，或明确写"未建立"
- [ ] 依赖层级全绿
- [ ] 存量失败已登记认领人
- [ ] 非 PASS 项逐条列了，有证据路径

---

### ■ G-M2 执行门

**通过条件**：§0 填全 + 依赖层全绿 + 三路证据齐（缺一路最高 PARTIAL）。
**不通过的最常见原因**：跑的是失败的 L0，却宣称模块通过（坑 5）。

---

### S6 填 04-准出卡

12 项检查，其中 9～12 是 v1.1 新增硬条件：

| # | 检查项 |
|---|---|
| 9 | §0 自动化健康度：依赖层级全绿且有时间戳 |
| 10 | 01 §5 裁决冲突全部闭环 |
| 11 | 全部 P0 VP 完成 VP 评审 |
| 12 | 反向矩阵无 P0 处于「已存在未跑」或「缺口」 |

**任一为"否" → 不得判 `准出`**，只能 `条件准出`（产品签字写明接受理由）或 `阻断`。

```bash
node tools/check-module.mjs modules/{FEAT-XX}-{slug} --gate=M3
```

---

### ■ G-M3 准出门

**通过条件**：12 项全过 + 三签（测试/产品/开发知会）。
**纪律**：`条件准出` 累计 2 次 → 下一轮强制阻断。

---

### S7 准出后（决定这套流程有没有长期价值）

| 动作 | 为什么 |
|---|---|
| 模块状态改 `已准出`，入**回归基线池** | 后续模块接入前要跑它 |
| 新增/修改的自动化登记进 `run-suite.ts` suite 列表 + 打 tag | 不登记，下一轮必漏 |
| 下一个模块 S0 之前，先跑一次**基线 smoke** | 这是分批交付下唯一能防"最后集成十连爆"的办法 |
| 裁决冲突若改了用例，同步更新 V5 工作簿 | 否则下个模块又踩同一个过期用例 |

## 三、常见错误对照（试点实测）

| 错误做法 | 后果 | 正确做法 |
|---|---|---|
| 表名从 Mapper 类名推断 | DB 快照验证无效 | S1 实测 grep |
| change 名抄旧台账 | 回归范围判错 | S1 实测 ls |
| VAL 不枚举直接拆 | 漏拆 20%+ | S2 先 grep 枚举 |
| VP 自己定级就完事 | 优先级错，重点测偏 | S2 产品确认 |
| V5 用例不导出 | "无用例"误判 | S3 必导出 |
| 用例过期照跑 | 测的是旧规则 | S3 对账，冲突归 E 类 |
| 有测试文件就算覆盖 | 门禁虚高 | S4 四态，只认已通过 |
| L0 是红的还说模块过了 | 准出建在沙上 | S5 先跑后填 |
