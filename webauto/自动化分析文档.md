## 3. 自动化流程的实现方式

### 3.1 分层设计

测试执行链路如下：

```text
tests 测试用例
  → business 业务流程编排
    → pages 页面对象
      → common AntD/Playwright 组件助手
        → 浏览器页面
```

数据准备由 `data/factory.py` 统一提供，测试层只负责编排动作和业务断言。

### 3.2 配置和运行入口

运行环境由 `--base-url` 或 `WEBTEST_BASE_URL` 指定，默认地址为 `http://localhost:8090`。默认登录账号为 `admin/admin123`，可通过 `WEBTEST_USERNAME`、`WEBTEST_PASSWORD` 覆盖。

生产主数据支持环境变量覆盖：

```powershell
$env:WEBTEST_PROD_JACKET_PREFIX = "PTG"
$env:WEBTEST_PROD_AIRBAG_PROFILE = "气囊 A型"
$env:WEBTEST_PROD_SENSOR_PROFILE = "传感器 A型"
$env:WEBTEST_PROD_FIRMWARE = "85cm"
$env:WEBTEST_PROD_INFLATOR_PROFILE = "充气发生器 A型"
```

全量主流程执行命令：

```powershell
cd E:\proptest\webauto\webtest
py -3.11 -m pytest -m mainflow -vv --base-url=http://localhost:8090
```

### 3.3 全局 fixture 与运行取证

`webtest/conftest.py` 重写了 Playwright 的 `context/page` fixture，统一完成以下工作：

- 创建浏览器上下文；
- 开启录屏；
- 失败时自动保存整页截图；
- 将截图和录屏附加到 Allure；
- 成功用例自动删除录屏，避免产物无限增长。

`logged_in_page` fixture 会先执行真实 UI 登录，再确保生产用例依赖的 `PTG` 衣体资料存在。

### 3.4 页面对象层

`pages/` 目录封装路由、定位器和页面动作。例如：

- `pages/base.py`：通用导航和定位能力；
- `pages/login_page.py`：登录页；
- `pages/production_intake_page.py`：衣体入库；
- `pages/production_assembly_page.py`：部件组装；
- `pages/production_inspection_page.py`：质检工作台；
- `pages/product_list_page.py`：产品列表和产品详情；
- `pages/part_tracing_page.py`：部件追溯；
- `pages/order_*.py`：订单创建、列表、详情和寄送；
- `pages/order_batch_print_page.py`：运单批量生成。

页面对象中包含必要的可见性等待和 UI 状态检查，但业务结果断言主要集中在 `tests/` 层。

### 3.5 Ant Design 组件助手

`common/antd.py` 封装了被测系统常用的 Ant Design Vue 4 交互：

- 表格行定位和按文本过滤；
- 弹窗、确认框和消息提示；
- 表单字段填写；
- Select 下拉选项查找；
- 虚拟滚动列表分段扫描；
- 按钮点击和 Tag 文本读取。

其中虚拟滚动处理是必要的：Ant Design Select 默认只渲染可见区域的选项 DOM，排在后面的选项无法被 Playwright 直接定位。

### 3.6 业务流程层

`business/` 负责把多个页面动作组合成可复用的业务前置链路，避免每条用例重复编写建单、入库、组装和质检步骤。

- `auth_flow.py`：执行真实 UI 登录。
- `production_flow.py`：提供衣体入库、部件组装、质检登记，以及一次性准备“已质检生产链”的 `prepare_inspected_products()`。
- `order_flow.py`：先通过 UI 新建客户和订单，再进入订单详情建立寄送准备，返回订单号、寄送号与产品编号。
- `base_flow.py`：保存 `page` 和 `settings`，供各业务流程继承。

生产链是多个模块的共同前置数据。产品列表和部件追溯用例先调用 `ProductionFlow.prepare_inspected_products()`，订单列表和运单生成用例则在已质检产品的基础上继续创建订单。由此形成如下可追踪链路：

```text
衣体编号
  → 组装部件编号
  → 质检通过产品
  → 客户与订单
  → 寄送准备
  → 批量运单文件
```

`OrderFlow.create_order()` 不写死商品名称，而是从页面可用商品中动态选择；订单数量由 `len(production.eligible_products)` 决定，避免生产数据变化后数量断言失真。

### 3.7 测试数据工厂

`data/factory.py` 统一生成会写入业务系统的测试数据，目前使用冻结的 `dataclass` 描述测试对象：

- `PartProfileData`：部件资料；
- `ValueData`：基础数据、作业选项；
- `CustomerData`：公司、地址、联系人、支店；
- `OrderData`：客户订单号、颜色备注、备注；
- `ProductionChainData`：衣体编号、部件编号和可质检判定。

每条数据都带有“时间戳 + UUID 片段”的唯一标识，并统一使用 `AUTO-WA-*` 前缀，便于检索测试产生的残留数据。客户编号、订单号、寄送号、制造番号等由系统生成，不进行人工伪造。

生产链固定生成 3 台产品：

1. 第 1 台包含气囊、传感器和 1 个充气发生器；
2. 第 2 台包含气囊、传感器和 2 个充气发生器；
3. 第 3 台只安装气囊，用于制造“不合格/未完成”边界。

其中“最低构成齐全”的判定条件是同时具备 `airbag`、`sensor`、`inflator_1`，因此前两台可进入质检，第 3 台只能用于验证在制、缺失部件和过滤逻辑。

生产主数据支持通过环境变量覆盖衣体前缀、气囊资料、传感器资料、固件版本和充气发生器资料。代码会对空值做启动校验，避免在缺少主数据时产生难以定位的页面失败。

### 3.8 前置数据与 fixture

`logged_in_page` fixture 完成两件事：

1. 通过登录页执行真实登录，而不是绕过 UI 注入 token；
2. 调用 `ensure_seed_data()`，确保后端存在启用的 `PTG` 衣体资料。

`ensure_seed_data()` 会从浏览器 Cookie 中读取 `Admin-Token`，在页面内调用后端接口查询衣体资料；若不存在则创建，并在创建后再次查询确认。这里显式补 `Authorization: Bearer <token>`，因为单纯依赖 Cookie 的 `credentials: include` 不会自动携带后端要求的 Authorization 请求头。

该前置机制解决了“生产用例依赖固定 seed data”的问题，但仍有环境约束：

- 依赖 `/dev-api/prop/part-profile/*` 接口路径；
- 只自动保障 `PTG` 衣体资料，其他气囊、传感器、固件和充气发生器资料必须在环境中预先存在；
- 需要在可以写入测试主数据的环境运行，不能直接指向生产环境。

### 3.9 断言与等待策略

当前用例主要采用以下四类校验：

1. **Playwright 自动等待断言**：使用 `expect(locator).to_be_visible()`、`to_contain_text()`、`to_have_text()`、`to_have_count()`，依赖框架轮询，避免固定 sleep。
2. **业务反馈断言**：通过 `wait_for_feedback()` 同时扫描 Ant Design message、notification 和 alert，匹配“追加しました。”“同じ値が登録済”等业务文案。
3. **接口响应断言**：寄送抽屉录入产品时监听 `/prop/shipment/{id}/products`，校验 `failures` 为空且产品出现在 `added` 中；切换承运商时监听寄送更新接口。
4. **数据一致性断言**：把测试数据工厂中的制造番号、部件编号、订单号、数量与页面行数据逐项比对，而不是只判断“页面有内容”。

断言主要放在 `tests/` 层。页面对象负责定位、动作和必要的响应等待，并返回文本、行定位器或结构化数据。`common/checks.py` 提供软断言收集器，但当前 11 条主流程未使用。

页面对象还封装了 Ant Design Vue 4 的常见交互：

- 通过 `.ant-modal:visible`、`.ant-drawer-content:visible` 限定当前可见弹层；
- 对虚拟滚动 Select 分段滚动并查找选项；
- 用 `force=True` 绕过 Ant Design 动画导致的 stability 检测；
- 对表格行、Tag、表单字段和按钮提供统一辅助方法。

### 3.10 中文测试点与 Allure

每条测试都遵守仓库的 `AGENTS.md` 规范：

- 文件顶部定义中文 `TEST_POINT`；
- 通过 `pytest.mark.parametrize(..., id=TEST_POINT)` 让 `pytest -vv` 直接显示中文测试点；
- 使用中文 docstring 描述测试点和验证内容；
- 步骤与断言分别使用 `# 步骤 N：`、`# 断言 N：`；
- 添加 `@allure.epic`、`@allure.feature`、`@allure.story`、`@allure.title` 和 `severity`。

`pytest.ini` 开启了 `disable_test_id_escaping_and_forfeit_all_rights_to_community_support`，以避免中文用例 ID 被转义为 `\uXXXX`。Allure 报告因此可以直接按“基础设置、客户管理、产品生产、产品管理、订单管理”等中文分类浏览。

## 5. 基础设置与客户主数据回归细节

### 5.1 FEAT-01 客户管理

用例先新建一个唯一公司，同一弹窗内连续录入一个地址和一个联系人，再检查保存后的公司详情：

- 系统自动生成 `C + 数字` 格式的客户编号；
- 邮编 `1040033` 展示为 `〒104-0033`；
- 地址 1、地址 2、联系人姓名和电话均正确回显；
- 新建支店时“所属会社”由上下文带入，支店获得独立客户编号和独立地址/联系人；
- 修改公司名称后，公司编号保持不变；
- 返回列表按新名称查询时，公司行命中并自动展开支店行，公司和支店均显示“直販”。

该用例覆盖了客户主档最常见的新增、层级、编辑和查询场景，但没有覆盖客户删除、历史客户补录、代理店区分、分页和重复公司名称提示。

### 5.2 FEAT-02 部件资料

用例生成唯一的部件名称、规格、厂商和编号前缀，完成新增后在列表校验规格和“有効”状态；随后修改规格与厂商，并验证列表立即回显；最后执行“無効 → 有効”状态切换。它覆盖了部件资料的基本生命周期，但没有覆盖编号前缀冲突、必填校验、同种别同品名拦截和分页查询。

### 5.3 FEAT-03 基础数据

当前只覆盖“传感器版本号”这一类基础数据：

1. 新增唯一版本号；
2. 再次提交相同值，校验 `同じ値が登録済` 提示且列表中仍只有 1 条；
3. 停用后 Tag 变为“無効”；
4. 启用后恢复“有効”。

FEAT-03 中的其他基础数据类型尚未纳入当前自动化。

### 5.4 FEAT-04 作业选项

用例选择“処置内容 / センサ”范围新增唯一选项，校验列表来源为“管理者”；随后验证重复值被拦截、状态可停用和重新启用。NG 选项、其他作业选项分类及受付快捷选项未覆盖。

## 6. 生产链回归细节

### 6.1 FEAT-05 衣体入库

用例先选择启用的 `PTG` 衣体资料，然后执行以下链路：

1. 单个加入第 1 台，候选行出现且状态为“入庫待ち”；
2. 再次输入同一编号，命中“この番号はすでに今回の入庫候補に含まれています。”，候选数仍为 1；
3. 输入连续范围，系统只补齐未加入的编号，最终候选数为 3；
4. 确认入库，页面提示“成功 3件、スキップ 0件、失敗 0件”，候选清单清空；
5. 进入部件组装页按同一范围检索，3 台产品均可见，证明入库已真正成立。

这里不仅验证按钮和提示，还通过下游页面反查产品，能发现“页面提示成功但产品未落库”的问题。

### 6.2 FEAT-06 部件组装

用例先完成 3 台衣体入库，再进入组装页：

- 选择衣体、气囊资料，并设置气囊、传感器、固件、充气发生器默认资料；
- 按测试数据中的列号逐台逐格录入部件编号；
- 完成计数断言为 `(2, 3)`，即 3 台中只有前 2 台达到最低构成；
- 所有产品行的 `.cell-error` 数量为 0；
- 重新打开页面并按同一范围检索，已录入的部件仍存在，未录入列保持为空。

这一用例验证了录入、最低构成计数和持久化，但没有覆盖非法部件编号、重复绑定、删除部件、并发编辑和超长范围。

### 6.3 FEAT-07 质检工作台

用例在完成 3 台入库和组装后按范围筛选：

- 只有 2 台齐全产品进入待质检清单，状态为“検査登録可”；
- 只安装气囊的第 3 台产品不出现在清单中；
- 勾选 2 台后，页面已选数同为 2；
- 批量确认提示“成功 2台、失敗 0台”，成功产品从清单移除；
- 再以已质检编号单件筛选，页面给出不可登记提示，原清单不会被错误替换。

## 10. 风险与待确认问题

### 10.1 P1：运单承运商断言与注释、后端行为冲突

文件：`tests/test_order_batch_print_mainflow.py`

- 第 89 行注释：承运商已被批量生成改写为 `佐川急便`；
- 第 91 行断言：`drawer.carrier_text() == "ヤマト運輸"`；
- 测试 docstring 又写“寄存档承运商不变”。

同一用例中存在三种口径：注释说已改写，断言说不改写，docstring 说文件版本变化但寄存档不变。

本次同时核对了后端当前实现：

- `PropShipmentDocumentService.java:189` 在生成成功后调用 `mapper.documentCarrier(...)`；
- `PropShipmentMapper.xml:105` 直接把 `prop_shipment.carrier` 更新为本次承运商。

因此在当前后端代码下，生成 `佐川急便` 面单后，寄送承运商应变为 `佐川急便`，第 91 行断言存在失败风险。2026-11-06 的历史通过结果不能排除“当时后端版本与当前不同”或“该断言未真正覆盖目标行为”的可能。

处理建议：由需求负责人确认“批量生成是否应回写寄送承运商”，然后让 Spec、后端、测试注释和断言保持一致。若应回写，断言改为 `佐川急便`；若不应回写，应修正后端并补充“回写失败/不更新”的反向验证。

### 10.2 P1：运单下载使用伪 Download，存在假阳性

文件：`pages/order_batch_print_page.py:67`

当前实现监听 `/prop/shipment/batch-labels` 的 POST 响应，将 `response.body()` 直接写入临时 `.xlsx`，再返回一个内部 `_FakeDownload`：

- 没有捕获浏览器真实下载事件；
- 文件名固定为 `送り状一括生成.xlsx`；
- 只断言后缀和文件大小，没有解析 XLSX；
- 即使响应体不是有效 Excel，只要非空也可能通过；
- 临时文件没有清理。

这会降低“面单可以正常下载且内容正确”这一核心业务结论的可信度。建议至少校验 `PK` 文件头和 ZIP/XLSX 结构，使用 `openpyxl` 读取工作表、行数和关键字段，并确认份数 2 是否真的产生对应页数或张数。若前端使用 fetch + Blob，应通过页面脚本或下载事件验证浏览器实际生成的 Blob 内容，而不是用响应体替代整个下载链路。

同一方法第 94 行保留 `time.sleep(3)`，第 97 行保留 `[DEBUG]` 输出，也应改为对成功提示或接口结果的显式等待，并移除调试输出。

### 10.3 P2：测试数据全部保留，依赖共享环境的初始状态

11 条业务用例都标记为 `destructive`，会持续新增客户、订单、产品、部件、寄送和文件记录。代码通过唯一时间戳降低编号冲突，但没有清理机制、数据库快照或租户隔离。

短期影响是测试环境数据膨胀；长期影响包括列表查询变慢、分页和总量断言受历史数据影响、共享环境被其他人员操作干扰。建议在独立测试库上运行，并在套件开始前恢复快照或在结束后按 `AUTO-WA-*` 前缀清理。

### 10.4 P2：定位器高度依赖日文文案、AntD DOM 和列序号

例如：

- `order_batch_print_page.py` 使用 `td:nth(4)` 读取台数；
- 成功提示依赖 `追加しました。`、`同じ値が登録済`、`ヤマト運輸` 等日文原文；
- 多个页面依赖 `.ant-table-row`、`.ant-tag`、`.ant-drawer-content` 等组件类名。

这些定位方式对 UI 改版、文案调整、表格列顺序变化和组件库升级较敏感。建议优先使用稳定的 `data-testid`、ARIA role/name 或业务接口返回的稳定标识；确实需要日文文案时，把文案集中到契约卡或页面对象常量中。

### 10.5 P2：seed data 保障逻辑不能处理“PTG 已存在但被停用”

`data/factory.py` 的 `ensure_seed_data()` 通过“启用衣体列表”判断 `PTG` 是否存在。如果环境中已有 `PTG` 但处于停用状态：

1. 查询不到启用记录；
2. 创建请求可能因同种别同品名或同前缀被拒绝；
3. 创建后的校验仍查询启用列表，继续失败；
4. fixture 抛出 `RuntimeError`，所有生产用例无法启动。

代码注释声称“即使已注册也视为成功”，但实际流程没有重新启用已有资料。建议改为按部件前缀查询全部状态；若存在但停用，则显式启用或给出可操作的诊断信息。

### 10.6 P2：缺少 CI、环境启动和数据重置编排

当前没有流水线配置，也没有自动启动前端、后端、数据库或浏览器的脚本。测试结果依赖人工环境，历史 Allure 报告可能与当前代码不同步。建议把“环境准备 → 数据库重置/seed → 启动服务 → 运行 `mainflow` → 生成 Allure → 归档截图/录屏”纳入 CI。

### 10.7 P3：数据生成的碰撞概率虽低但未完全消除

测试数据使用“秒级时间 + 4 位 UUID/2 位随机数”生成。常规串行运行足够，但短时间内并行执行多个 worker 时，客户、订单、部件前缀仍存在极小碰撞概率。若后续引入 `pytest-xdist`，应改为完整 UUID、进程 ID 或数据库序列。

## 11. 改进建议

### 11.1 优先修复影响可信度的问题

1. 统一运单承运商需求口径，修正第 91 行断言、第 89 行注释和 docstring，必要时同步后端。
2. 用真实可验证的 XLSX 文件替换 `_FakeDownload`，校验文件结构、工作表、首页/张数和关键字段。
3. 移除 `time.sleep(3)`、`[DEBUG]` 和临时文件残留，改为等待明确 UI 或接口状态。
4. 修正 `ensure_seed_data()` 对“已存在但停用”的 PTG 的处理，避免套件因共享环境状态无法启动。

### 11.2 建立可重复的运行环境

- 为自动化使用独立数据库和固定 seed 数据；
- 每次运行前恢复数据库快照，或运行后按 `AUTO-WA-*` 前缀清理；
- 固定前端、后端、数据库和浏览器版本；
- 在 CI 中自动启动服务、执行 `pytest -m mainflow`、生成并归档 Allure 报告；
- 失败时保留截图、录屏、请求响应和必要日志。

### 11.3 提升定位稳定性

- 推动前端为关键表格列、状态、寄送号、制造番号、下载按钮增加 `data-testid`；
- 用表头名称映射列索引，替代固定 `td.nth(N)`；
- 将日文业务文案集中到页面对象或契约卡，避免散落在所有用例中；
- 对表格分页、虚拟滚动和异步刷新增加可观测的接口或 DOM 就绪条件。

### 11.4 扩展回归范围

建议按业务风险补充：

1. 寄送确认、运单号回写、有效出荷数和订单履约状态；
2. 订单编辑、取消、代理店客户、多商品行和非法数量；
3. 客户支店编辑/删除、历史客户和重复公司提示；
4. 生产异常：重复部件、非法编号、部分入库失败、并发保存；
5. 质检 NG、部分成功、撤销和权限隔离；
6. 权限、未登录、接口越权、重复提交和并发修订冲突；
7. 产品列表分页、筛选组合和大数据量性能；
8. 运单份数边界、模板异常、下载失败和 XLSX 内容正确性。

### 11.5 增强取证能力

现有失败截图和录屏已经比较完善，后续可在关键断言点附加：

- 订单号、寄送号、制造番号等业务键；
- 寄送准备和批量生成的接口请求/响应摘要；
- 数据库中的承运商、寄送状态、有效出荷数；
- XLSX 文件的结构和关键单元格；
- 失败时的页面 URL、浏览器控制台错误和网络失败请求。

## 12. 结论

`E:\proptest\webauto` 已经形成一套结构清晰、可复用的高价值 Web UI 主流程回归套件。它采用 pytest + Playwright + POM + 业务流程层 + 数据工厂的组合，能够把衣体入库、部件组装、质检、产品查询、部件追溯、客户、订单、寄送准备和运单生成串成真实数据链，并通过 Allure、录屏和失败截图保留执行证据。

当前最有价值的成果是 11 条跨模块端到端主流程，以及统一的中文测试点、唯一测试数据和自动诊断能力。现有历史报告显示 13/13 通过，但由于本次没有重新执行破坏性用例，且缺少 CI 和数据重置，不能把该结果直接等同于当前版本的持续质量保证。

在把该套件用于正式回归前，应优先解决运单承运商断言冲突和伪下载验证问题；随后补齐独立测试环境、数据清理、CI 编排和关键异常/权限场景。完成这些改进后，该工程可以从“可运行的主流程演示与回归辅助工具”提升为“可持续、可审计、可用于发布门禁的自动化回归体系”。
