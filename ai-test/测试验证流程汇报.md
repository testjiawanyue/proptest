# PROP 系统测试验证工作汇报

> 汇报日期：2026 年 10 月 19 日
> 适用范围：PROP 气囊管理系统 V2.1 的需求、代码与测试用例验证工作
> 阅读对象：项目管理人员、开发与测试团队、质量负责人

---

## 一、我们在做什么

这个项目采用了一套「AI 辅助的三方对照验证」方法。简单来说，就是先把三件事情分别搞清楚，再互相对照：

1. **需求说了什么** —— 把需求规格说明书逐条拆解成结构化的需求清单；
2. **代码实际做了什么** —— 不猜、不看注释，只根据真实代码梳理出系统实际实现的行为；
3. **测试用例在测什么** —— 把全部测试用例整理出来，检查每条用例测的到底是什么。

然后做三个方向的互相对照：

- 需求 ↔ 代码：**说要做的，做了没有？**
- 需求 ↔ 用例：**说要做的，测了没有？**
- 代码 ↔ 用例：**实际做的，测得对不对？**

整个过程是**静态分析**——不启动系统、不执行测试，而是像"阅卷"一样逐条比对。它的价值在于：在真正投入测试执行之前，提前发现需求没实现、测试没覆盖、用例和代码相互矛盾这三类隐患。

为保证结论可信，整套方法遵守几条铁律：

- 只认明确证据，不靠方法名、注释或"行业惯例"猜测；
- 不能用"需求里有"来推断"代码已经做了"，也不能反过来；
- 证据不足就明确标注"无法确认"，绝不为了好看而判通过。

## 二、验证流程全景

整个验证分八个阶段，可以理解为"建三份档案、做三次对照、出一份总报告"：

```
  第一阶段：建档（各自独立，互不参考）
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │  ① 需求建档  │  │  ② 代码建档  │  │  ③ 用例建档  │
  │ 需求拆成106条│  │ 梳理代码实际 │  │ 分析1188条  │
  │ 并编号管理   │  │ 行为并编号   │  │ 并修复问题  │
  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
         │                │                │
  第二阶段：对照（两两比对，再找三方都对不上的）
         ▼                ▼                ▼
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │ ④ 需求↔代码 │  │ ⑤ 需求↔用例 │  │ ⑥ 代码↔用例 │
  │ 实现了没有  │  │ 覆盖了没有  │  │ 测得对不对  │
  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘
         └────────┬───────┴────────┬───────┘
                  ▼                ▼
           ┌─────────────┐  ┌─────────────┐
           │ ⑦ 三方交叉   │  │ ⑧ 总报告    │
           │ 找出四类脱节 │  │ 质量门禁结论│
           │ （待执行）   │  │ （待执行）  │
           └─────────────┘  └─────────────┘
```

### 各阶段做了什么

**① 需求建档（已完成）**
把 20 个业务功能模块的需求说明书拆解成 106 条编号需求。每条需求都写清：正常怎么做、出错怎么办、有哪些业务规则、数据会怎么变、谁能操作、边界在哪里、怎样算验收通过。需求里说不清楚的，列入"需求疑问清单"，不自行脑补。

**② 代码建档（部分完成）**
沿着"接口 → 业务处理 → 数据库"的链路，逐行阅读代码，记录系统**实际**的行为，每个重要判断分支都编号。目前已完成"基础设置"和"客户管理"两个模块，其余 18 个模块的代码建档尚未开展。

**③ 用例建档与修复（已完成）**
对原有 1188 条测试用例逐条分析，检查有没有目的不清、和需求对不上、内容相互矛盾的问题。随后依据需求规格定点修复了 106 条用例行——只改错不改结构，不新增、不删除、不合并。修复后形成当前在用的 V5 版用例集，共 1257 条。

**④ 需求↔代码对照（部分完成）**
逐条需求问："代码实现了吗？"结论分三档：通过 / 部分实现 / 未实现，并给出具体证据。目前覆盖客户管理和基础设置两个模块的需求。

**⑤ 需求↔用例对照（已完成）**
逐条需求问："有用例测吗？测全了吗？"结论分四档：覆盖充分 / 覆盖不足 / 完全缺失 / 无法设计验证。106 条需求全部对照完毕，另对"主流程是否真的有人测"做了专项复核。

**⑥ 代码↔用例对照（部分完成）**
逐条用例问："你预期的那样，代码真的是那样做的吗？"结论分四档：代码支撑 / 部分支撑 / 明确冲突 / 无法确认。目前完成基础设置 106 条、客户管理 115 条用例。

**⑦ 三方交叉验证（待执行）**
把三份档案串成一条链：需求 → 代码 → 用例，系统找出四类脱节问题（见第四节），并按严重程度分 P0～P3 级。

**⑧ 总报告（待执行）**
汇总所有对照结果，给出最终质量门禁结论：放行 / 阻断 / 需人工评审。

## 四、这套流程能发现哪些类型的问题

### 类型 1：需求本身的问题
- 需求描述含糊、自相矛盾、没说清楚的地方 → 列入疑问清单，需要业务方澄清；
- 需求之间的依赖关系 → 提前识别改动影响面。

### 类型 2：说了没做（实现缺口）
需求有明确要求，但代码没实现或只实现了一半。例如：

- 需求要求"历史导入的老客户沿用原编号"，代码里只有兼容的存储结构，却没有导入程序，无法证明这条规则真正落地；
- 需求要求客户名称、支店名称不能重复，代码里**没有任何重复检查**。

### 类型 3：做了没测（覆盖缺口）
需求（或代码行为）存在，但没有对应的测试用例。目前已发现：

- 106 条需求中，88 条覆盖充分，17 条覆盖不足，1 条完全缺失；
- 覆盖不足主要集中在**权限场景**（多个看板类需求缺"允许角色/禁止角色"对照验证）和**边界值场景**；
- 专项复核确认：唯一真正缺主流程验证的是**受付工作台**——缺少"跳转后恢复操作位置"和"端到端完整受理链路"的用例。

### 类型 4：测的和做的不一样（用例与代码冲突）
用例的预期结果和代码实际行为**正好相反**，这类用例一旦执行必然失败，或者更糟——误导判断。目前完成判定的 221 条用例中：

- 客户管理：115 条里 **15 条冲突**（13%）；
- 基础设置：106 条里 **6 条冲突**。

典型例子：

- 用例说"传感器规格留空也能保存"，代码实际会**拒绝**；
- 用例说"重名保存会失败"，代码实际**不做重名检查**，可以保存；
- 用例说"被引用的资料不能停用"，代码实际**不检查引用关系**；
- 用例说"并发编辑会提示数据已被他人修改"，代码实际**后保存的会静默覆盖先保存的**；
- 还有 2 条用例自身就矛盾：标题、测试点、预期结果方向不一致。

这类冲突需要逐条裁定：到底是代码要改，还是用例要改。

### 类型 5：静态分析无法确认的问题
以下内容被如实标注为"无法确认"，不会被假装判过，需要留到实际运行时验证：

- 页面交互细节（按钮是否置灰、取消是否真的不存、浏览器缓存）；
- 登录状态、角色权限的实际配置；
- 跨模块联动、历史数据展示等需要完整环境才能验证的行为。

### 类型 6：用例自身的质量问题
- 需求说 A、用例写 B 的"过期用例"——已修复 106 行；
- 目的不清、需求对不上号的用例——已在分析阶段标记。

## 五、这套流程不能发现什么

说清楚边界，避免误用结论：

1. **不代替测试执行**。所有结论都是"按证据推断代码会这样表现"，不是"实际运行确实如此"；
2. **不验证运行表现**。性能、并发真实表现、第三方接口真实调用都不在范围内；
3. **大部分模块还没做代码建档**。生产、订单、寄送、受付、作业、报告等 18 个模块目前只能做"需求↔用例"对照，无法判断实现情况和用例对错。

## 六、下一步建议

1. **补齐最后两个环节**：完成三方交叉验证和总报告，得出整体质量结论（放行 / 阻断 / 需评审）；
2. **继续代码建档**：按业务优先级推进其余模块，让更多需求能做"实现了没有"的判定；
3. **闭环 21 条冲突用例**：逐条裁定改代码还是改用例，明确责任人和期限；
4. **补充受付工作台主流程用例**：这是目前确认的唯一主流程缺口；
5. **把"无法确认"项转成执行清单**：作为后续真实环境测试的输入，避免遗漏。

## 七、一句话总结

> 这套验证方法把"需求、代码、用例"三方拉到一起对账：账已经对清了**需求与用例**，发现了 **21 条用例与代码的明确冲突**和 **1 个主流程覆盖缺口**；代码这条线完成了两个模块，交叉验证和最终结论待补齐。
