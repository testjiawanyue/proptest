# 端到端自动探索测试验证方案
## —— 基于 Playwright + Agent 架构（PROP 项目）

> 版本：V1.0　日期：2026-10-19
> 定位：在已有「静态三方验证体系」（需求基线 / 代码行为模型 / 用例模型）之上，补齐**运行时验证**能力，形成"静态分析 + 动态探索"的完整质量闭环。

---

## 一、为什么做、解决什么问题

现有静态验证已经把"需求、代码、用例"三方对账，但它有两个天然边界：

1. **静态判不了的问题被搁置**：前端交互、登录态、权限实际配置、跨模块联动、历史数据展示等约 20% 的用例被标为"无法确认"；
2. **静态结论未被运行证实**：21 条"用例与代码冲突"的裁定、88 条"覆盖充分"的需求，都只是证据推断，没有真实执行背书。

本方案用 **Playwright 驱动真实浏览器**、用 **Agent 架构赋予其自主探索与判断能力**，实现：

- 把静态体系的"无法确认"项变成运行时的"已验证/已证伪"；
- 自动执行探索式测试，发现脚本化用例之外的缺陷（状态污染、流程死路、异常提示缺失）;
- 每次探索都产出带证据（录像、截图、网络请求、数据库前后快照）的报告，回灌到质量门禁。

### 2.2 各角色职责

**① 规划 Agent（Planner）**
- 输入：需求基线、代码行为模型、用例集、历史探索状态图。
- 工作：把验证目标拆成一个个 15～30 分钟的**探索任务单（Charter）**，例如"验证客户支店级联删除后详情页表现"或"探索受付工作台在大番号为空时的行为"。
- 排优先级：静态冲突项 > 无法确认项 > 核心主流程 > 边界与权限 > 自由探索。
- 避重：查询状态图，跳过已充分探索的区域。

**② 探索 Agent（Explorer）—— 核心执行者**
- 通过 Playwright 操作真实浏览器，每一步循环为：**感知 → 决策 → 行动 → 观察**。
  - 感知：抓取页面无障碍树（accessibility tree）+ 关键 DOM 属性 + 截图，压缩成模型可理解的页面摘要；
  - 决策：根据任务单目标和当前页面状态，选择下一个动作（点哪里、填什么、验证什么）；
  - 行动：调用封装好的 Playwright 动作工具集（点击、填写、选择下拉、翻页、模拟扫码输入等）；
  - 观察：记录动作后的页面变化、网络请求、控制台报错。
- 内置**护栏**：禁止操作范围外菜单（如系统管理的数据清空）、禁止修改非测试数据、单任务步数上限、检测到生产特征立即中止。

**③ 判定 Agent（Oracle）—— 解决"怎么算对"的问题**
- 三级判定，按成本从低到高：
  1. **规则判定**（硬断言）：HTTP 状态码、接口返回码、页面出现/消失指定文本、数据库字段值（通过 DB 探针直接查 MySQL 验证数据变化）；
  2. **基线对照**：把观察到的行为与需求基线/代码行为模型逐条比对，判定符合 / 违背 / 基线未覆盖；
  3. **语义判定**（LLM 判断）：页面提示是否友好、流程是否合理等软性问题，结论一律降级为"待人工复核"。
- 输出四档结论：**通过 / 失败 / 无法确认 / 基线外发现**（发现需求没写但系统有的行为）。

**④ 环境管理 Agent（Env Manager）**
- 负责每个任务开始前的**状态准备**：通过 SQL 脚本或后端 API 快速造数（客户、订单、产品、受付单等），任务结束后按需回滚或打快照；
- 维护测试账号与角色矩阵（管理员、普通作业员、无权限角色），供权限类探索使用；
- 保证任务之间不互相污染：独立浏览器上下文 + 数据命名隔离 + 定时环境重置。

**⑤ 报告 Agent（Reporter）**
- 汇总所有任务的执行流、判定结论和证据，产出四类报告（见第五节）。

### 2.3 执行层：Playwright 封装

Playwright 不只是"点页面"，在本架构中它是**三路探针**：

| 探针 | 采集内容 | 用途 |
|---|---|---|
| 页面探针 | 无障碍树、DOM、截图、控制台错误 | 探索 Agent 感知 + 证据留存 |
| 网络探针 | 全部接口请求/响应（HAR）、状态码、耗时 | 验证前端操作触发了正确的后端调用；捕捉 500 错误 |
| 数据探针 | 操作前后对 MySQL 的定点查询快照 | 验证数据变化（版本号 +1、状态字段切换、级联删除）——这是判定 Oracle 最硬的证据 |

工程要点：
- 每个任务独立 BrowserContext，全程开启 **Trace（含录像、DOM 快照、网络日志）**，失败时一键回放；
- 动作工具集语义化封装（如 `createCompany(name)` 而非裸点击坐标），降低模型出错率；
- 登录态复用（storageState），RuoYi 验证码通过测试环境关闭或固定值绕过；
- 自动等待 + 有限重试，对抗前端加载抖动。

## 三、探索策略：Agent 怎么"逛"系统

四种策略按任务类型组合使用：

**策略 A：目标验证式（Verify）**
带着明确的 REQ/BR/用例编号去执行，例如复验 21 条静态冲突项。产出直接回写覆盖矩阵。这是前两个阶段的主力策略。

**策略 B：行为图引导式（Model-based）**
把代码行为模型的 BR 分支建成有向图，探索 Agent 沿图行走，优先走没走过的边。每到一个新状态就记录进**状态图**（页面指纹 + 数据状态哈希），逐渐长成系统的"探索地图"，可视化展示已探索/未探索区域。

**策略 C：边界与异常注入（Fuzz）**
对表单自动生成边界输入：空值、纯空格、超长字符串、特殊字符、Unicode 边界（正好贴合基线中"32 个码点"这类规则）、并发提交（两个浏览器上下文同时编辑同一记录，验证是否有覆盖提示）。

**策略 D：自由漫游（Monkey+）**
在已登录的受限范围内随机探索，目标是"撞"出意外：控制台报错、接口 500、页面卡死、返回后状态错乱。所有意外自动录证并提交判定 Agent。

## 四、针对 PROP 项目的验证落地计划

### 阶段 0：环境与底座（第 1～2 周）
- 搭建独立测试环境：后端 + MySQL + 前端 dev 服务，注入基础种子数据；
- 完成 Playwright 工程底座：登录封装、动作工具集、三路探针、Trace 录证；
- 实现判定 Agent 的规则判定层（接口断言 + DB 快照比对）；
- 试点任务：登录 + 首页看板渲染 + 客户公司新建（1 条端到端冒烟链路）。

### 阶段 1：静态结论运行时复验（第 3～5 周）
- 目标：把已有静态结论变成运行时证据，优先处理高价值项；
- 任务清单直接来自静态体系：
  - 21 条用例↔代码冲突项 → 逐条执行裁定，输出"改代码 or 改用例"的运行时证据；
  - 客户管理 + 基础设置约 27 条"无法确认"用例 → 前端交互、权限实际验证；
  - REQ-070 受付工作台主流程缺口 → 端到端主链路探索；
- 产出：复验报告 + 更新后的运行时覆盖矩阵。

### 阶段 2：已建模模块深度探索（第 6～9 周）
- 对客户管理、基础设置启用策略 B/C：行为图全边覆盖 + 边界注入 + 权限矩阵遍历（3 类角色 × 全部入口）；
- 并发专项：双上下文并发编辑客户/部件资料，验证静默覆盖问题（静态分析已提示无版本检查，运行时坐实）；
- 产出：缺陷报告批量提交 + 状态图第一版。

### 阶段 3：全模块扩展（第 10 周起，跟随静态建模进度）
- 静态代码建模每完成一个 Feature，动态探索跟进一个：生产 → 订单 → 寄送 → 受付 → 作业 → 报告；
- 建立**回归模式**：每次代码合入后，自动重跑受影响模块的目标验证式任务，对比前后状态图差异；
- 接入 CI：夜间全量探索 + PR 触发关键链路冒烟。

### 贯穿：安全与成本控制
- 仅允许在独立测试环境运行，连接串、账号硬隔离；
- 探索 Agent 每步行动前过护栏校验，危险操作（删除类批量操作）需任务单显式授权；
- 模型调用预算按任务单限额，状态图去重控制探索膨胀。

## 五、报告产出体系

每次探索批次产出四份报告，与静态体系口径对齐：

**① 探索执行报告（单次/每日）**
- 任务单完成情况、探索路径概览（状态图增量）、新发现状态数；
- 附件级证据：每个异常点附 Trace 回放链接、前后截图、接口请求/响应、DB 前后快照。

**② 缺陷报告（按发现即时产出）**
- 标准字段：标题、严重级（沿用 P0～P3）、关联 REQ/BR/用例编号、复现步骤（可直接转成 Playwright 脚本回放）、证据包、判定依据；
- 缺陷来源标注：冲突复验 / 覆盖补测 / 自由探索新发现。

**③ 运行时覆盖矩阵（持续更新）**
- 在静态覆盖矩阵基础上增加"运行时验证"维度：
  REQ → 静态覆盖（已有）→ 运行时通过 / 失败 / 未覆盖；
- 冲突项状态跟踪：21 条冲突各自的裁定进度与最终结论。

**④ 质量门禁汇总（迭代末）**
- 与静态体系的 T08 总报告合并：静态结论 + 动态结论 → 统一门禁（PASS / BLOCK / REVIEW）；
- BLOCK 条件升级：除静态 P0/P1 外，任一主流程运行时失败、数据一致性缺陷（如并发静默覆盖被证实）同样阻断。

报告形态：机器可读 JSON（供 CI 消费）+ Markdown/HTML 人读版；缺陷可直接同步到缺陷跟踪工具。

## 六、技术选型与工程结构

| 层 | 选型 | 说明 |
|---|---|---|
| 浏览器自动化 | Playwright（Node.js/TypeScript） | Trace 录证、多上下文并发、网络拦截成熟 |
| Agent 编排 | 轻量自研循环（感知-决策-行动）或 LangGraph | 核心是把页面摘要、动作工具、护栏做扎实 |
| 模型 | 当前主力编码/推理模型 | 探索决策与语义判定分层调用，控制成本 |
| 数据探针 | mysql2 直连测试库 | DB 前后快照是判定 Oracle 的硬证据 |
| 状态图存储 | SQLite/JSON 起步，量大后迁图数据库 | 页面指纹 + 数据哈希作为节点 |
| 报告 | JSON → Markdown/HTML 渲染，可选 Allure | 与静态报告同目录体系归档 |

建议工程目录划分：`agents/`（五个 Agent 实现）、`probes/`（三路探针）、`actions/`（语义化动作集）、`charters/`（任务单）、`state-graph/`（探索地图）、`reports/`（产出）、`guardrails/`（护栏规则）。

## 七、主要风险与对策

| 风险 | 对策 |
|---|---|
| 探索失控、重复走老路 | 状态图去重 + 任务单边界 + 步数上限 |
| 模型误判缺陷 | 三级判定分层，语义判定一律人工复核；硬证据（接口/DB）优先 |
| 测试数据污染 | 环境隔离 + 数据命名隔离 + 定时重置 + 造数脚本幂等 |
| 前端细节变动导致动作失效 | 语义化定位（角色/文本），禁止坐标和脆弱 CSS 选择器 |
| 运行成本膨胀 | 任务单预算制；规则判定免费层先过滤；探索增量优先 |
| 误伤真实环境 | 环境指纹识别，非测试环境拒绝启动；护栏白名单制 |

## 八、成功度量

- **复验完成率**：21 条冲突 + 27 条无法确认 → 100% 获得运行时结论；
- **运行时覆盖率**：已建模模块的 BR 分支运行时覆盖 ≥ 80%；
- **新发现缺陷数**：自由探索/边界注入带来的脚本外缺陷；
- **证据完整率**：100% 缺陷带可回放 Trace 与 DB 快照；
- **回归时效**：代码合入后受影响链路自动复验 < 30 分钟。
