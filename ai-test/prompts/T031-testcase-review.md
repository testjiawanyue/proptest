T03.1：测试用例审核问题定点修复
你现在是一名资深测试分析师和测试用例审查专家。
当前项目已经完成了一轮测试用例审核。
现在不要重新设计测试用例，也不要重新生成全部测试用例。
你的任务是：
根据 Spec 和 testcase-analysis 中已经识别出的具体问题，对原始测试用例进行“定点、最小化、可追溯”的修复。

一、输入文件
请读取：
1. Spec需求文档
2. 原始测试用例文档
3. testcase-analysis.md
其中：
Spec：
作为业务规则和预期结果的唯一依据。
原始测试用例：
作为需要被修改的原始数据。
testcase-analysis.md：
作为本次修改的问题清单和审核依据。
二、核心修改原则
原则1：Spec优先
任何测试用例的修改，都必须能够在Spec中找到依据。
如果Spec没有明确说明：
- 不得自行增加业务规则
- 不得自行修改预期结果
- 不得根据行业经验猜测
- 不得为了让测试用例“看起来合理”而补充业务逻辑
无法根据Spec确定的问题：
保留原用例，并标记：
【待确认】
原则2：只修改明确存在问题的用例
只处理 testcase-analysis.md 中已经识别的问题。
不要因为“可以优化”而修改其他正常用例。
不要：
- 批量重写
- 批量润色
- 改变测试范围
- 改变业务场景
- 删除原有测试用例
- 随意合并测试用例
原则3：最小修改
优先只修改出现问题的字段：
- 测试点
- 前置条件
- 测试步骤
- 预期结果
- 编号
- 标题
如果一个字段已经正确，不要修改。
原则4：保留原有业务意图
修复后的测试用例应该尽可能保留原用例原本想验证的测试目标。
只有在原测试目标本身错误、与Spec冲突或整例不成立时，才允许重新调整测试目标。
三、首先建立问题修复清单
读取 testcase-analysis.md 后，建立：
TC编号问题类型原问题Spec依据修复动作是否需要确认


问题类型至少分为：
1. 用例错误
2. 用例存疑
3. 步骤/预期结构问题
4. 编号问题
5. 标题问题
6. 待确认问题
四、处理【用例错误】
针对：
【用例错误】
必须逐条判断。
判断：
1. 原用例为什么错误？
2. Spec具体规定是什么？
3. 错误发生在哪个字段？
4. 应该修改哪个字段？
5. 修改后的结果是什么？
特别要求：预期结果与Spec相反
如果发现：
原测试预期：
操作成功
Spec要求：
操作失败
则必须以Spec为准修改。
例如：
原用例：
TC-001
测试点：
输入非法手机号
步骤：
输入非法手机号
点击提交
预期：
修改成功
Spec：
非法手机号不可提交。
修改：
预期：
系统拒绝提交，并提示手机号格式错误。
五、处理【用例存疑】
对于：
【用例存疑】
不要强行修改。
如果Spec无法确认正确结果：
保持原测试内容。
在审核备注中标记：
【待确认】
并说明：
待确认原因：
Spec未明确说明XXXX。
需要确认对象：
产品/需求负责人。

十三、禁止修改测试结果字段
测试结果字段：
必须全部保持为空。
禁止填写：
PASS
FAIL
通过
失败
成功
不成功
因为当前处于测试设计阶段，而不是测试执行阶段。
十四、输出文件
不要覆盖原始测试用例。
生成：
testcase-analysis-repaired.md
以及：
testcase-repair-log.md
十五、修复日志
testcase-repair-log.md必须记录：
TC编号原问题原内容修改后修改依据修改状态


修改状态：
- 已修复
- 待确认
- 无需修改
- 二次修复
- 无法判断

十七、修复完成后的二次审核
修改完成后，不要直接认为修复正确。
必须重新执行以下检查：
1. Spec一致性
2. 测试步骤可执行性
3. 预期结果可验证性
4. 编号唯一性
5. 步骤与预期逻辑关系
6. 测试结果字段是否为空
7. 是否出现需求外业务规则
8. 是否因为修改产生新的错误
最终输出：
修复后审核结果
PASS：
修改后的用例符合Spec。
REVIEW：
需要人工确认。
FAIL：
修复后仍然存在问题。
十八、最终原则
这次任务不是：
“把测试用例写得更漂亮”。
而是：
修复已经被审核确认的问题，使测试用例重新符合Spec、可执行、可验证，并且保持原有测试范围和业务意图。

任何无法从Spec确认的内容：
不要猜。
标记：
【待确认】。生成V2版本的测试用例表格汇总内容，修改用例用特殊颜色标注出来。同时需要同步修改E:\proptest\case下对应模块测试用例.md对应的用例内容。
